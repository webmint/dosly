## Medium Findings

### Lifecycle / Latent Runtime

- **`lib/features/settings/presentation/providers/settings_provider.dart:73`** — `late final` field reassigned in `build()`
  Evidence:
  ```
    late final StreamController<Failure> _errors;
  ```
  Why it's wrong: `build()` unconditionally executes `_errors = StreamController<Failure>.broadcast();` (line 89). A `late final` field may be assigned exactly once per instance. Riverpod retains the `Notifier` instance across rebuilds and re-invokes `build()` on it (this is why the docs warn against `late final` init in `build`). If `settingsNotifierProvider` ever rebuilds — e.g. `settingsRepositoryProvider` (autoDispose) recomputes because `sharedPreferencesProvider` is invalidated/re-overridden — the second `build()` hits the already-initialized `late final` and throws `LateInitializationError: Field '_errors' has already been initialized`. It is dormant today only because the dependency chain is stable in normal operation.
  Remediation: Drop `final` (`late StreamController<Failure> _errors;`) so reassignment on rebuild is legal, and guard the disposal so a rebuild doesn't double-close. (Riverpod also disposes the prior build's `ref.onDispose(_errors.close)` before re-running `build()`, so reassignment is the correct shape once `final` is removed.)
  Confidence: Likely

### Cross-File Contradictions / DRY

- **`lib/core/providers/shared_preferences_provider.dart:37`** — Prefs key set encoded twice across a layer boundary
  Evidence:
  ```
          allowList: <String>{
            'themeMode',
            'useSystemTheme',
            'useSystemLanguage',
            'manualLanguage',
          },
  ```
  Why it's wrong: These four key names are bare literals here, but the same four are the system-of-record constants `_kThemeModeKey = 'themeMode'`, `_kUseSystemThemeKey`, `_kUseSystemLanguageKey`, `_kManualLanguageKey` in `lib/features/settings/data/datasources/settings_local_data_source.dart:11–20` (the only code that reads/writes them). No compiler or `dart analyze` catches it. The dartdoc (lines 29–31) acknowledges the coupling ("The `allowList` mirrors the keys read by the settings feature") without enforcing it.

  Confidence: Certain

### Sensitive-Data Posture (Security)

- **`android/app/src/main/AndroidManifest.xml:2`** — `allowBackup` defaults to `true` for a PHI app (CWE-312 / CWE-530)
  Evidence:
  ```
      <application
          android:label="dosly"
          android:name="${applicationName}"
          android:icon="@mipmap/ic_launcher">
  ```
  Why it's wrong: The `<application>` element sets no `android:allowBackup`, so Android's default (`true`) applies — SharedPreferences (and any future on-device store) become eligible for Auto Backup to Google Drive and `adb backup` extraction. Only non-PHI UI flags live in prefs today, so live exposure is small, but the constitution treats storage-location drift as a Critical risk and mandates "Never persist health data with cloud sync without explicit opt-in." `allowBackup=true` silently widens the blast radius of any future drift to off-device backups without a conscious opt-in. Posture/defense-in-depth, hence Medium.
  Remediation: Add `android:allowBackup="false"` to `<application>` (and consider `android:dataExtractionRules` for Android 12+ / `android:fullBackupContent` with an explicit exclude list). Keeps present UI flags and any future medication store off Google's backup transport unless a feature consciously opts in.
  Confidence: Certain

### Comment / Doc Lies (load-bearing channel)

- **`lib/features/settings/presentation/providers/settings_provider.dart:75`** — `errors` getter dartdoc claims startup-load failures reach the UI; they are silently dropped
  Evidence:
  ```
    /// Broadcast stream of [Failure]s from the initial settings load and the
    /// four save mutators.
    ///
    /// The Left branch of the [build] load fold (a `Failure.unknown` when the
    /// cache read throws) and each Left from [SettingsRepository.saveX] are
    /// forwarded to this stream so a UI surface (e.g. [SettingsScreen]) can
    /// react via [settingsErrorsProvider].
  ```
  Why it's wrong: `build()` calls `_errors.add(failure)` (line 94) synchronously before any `settingsErrorsProvider` listener can subscribe, and a broadcast `StreamController` does not buffer events for absent subscribers. The startup-load failure is therefore permanently discarded — documented as accepted in MEMORY.md (spec 022 OQ-2). The dartdoc states the opposite: that the build-load Left "can react via [settingsErrorsProvider]." That is precisely the one case that cannot. (Same overstated claim at the library-level `settingsErrorsProvider` doc, line 213: "both the initial settings load and subsequent persistence (save) operations.") A maintainer trusting this would wrongly build startup-error UX on a channel that drops the event. **The lie in the doc is more dangerous than the accepted behavior.**
  Remediation: Reword both docs to state that only post-startup `saveX` failures are deliverable, and that the initial-load `Failure.unknown` emitted during `build()` is intentionally not surfaced here (cross-ref OQ-2). If startup-failure surfacing is ever required, the MEMORY-documented fix is `scheduleMicrotask(() => _errors.add(failure))` or a replay-buffered state field. Do not change behavior — only correct the claims. (Also fix the stale count: the doc says "four save mutators" but five methods feed the stream — `setThemeMode`, `setUseSystemTheme`, `setUseSystemLanguage`, `setManualLanguage`, `cycleThemeMode`.)
  Confidence: Certain
