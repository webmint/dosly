# Project Memory — dosly

## Project Identity
**dosly** is a personal cross-platform (iOS + Android) medication tracking app. Fully local — no backend, no accounts, no telemetry. Tracks medications, schedules, intake confirmations, and adherence history. Constitution at `constitution.md` is the source of truth.

## Project Structure
Greenfield Flutter app — `flutter create .` has run, scaffolding is in place. `linux/`, `macos/`, `web/`, `windows/` were removed (iOS + Android only). No feature code yet — first scaffolding step is `lib/core/error/failures.dart` per constitution Section 7.1.

## Architecture Decisions
<!-- Why decisions were made, not just what -->

- **Clean Architecture (data/domain/presentation per feature)** — chosen during `/setup-wizard`. Rationale: enforces dependency direction, makes domain logic unit-testable in pure Dart, isolates third-party SDK choices in `data/`.
- **`Either<Failure, T>` via fpdart** — chosen during `/setup-wizard`. Rationale: explicit error flow at repository boundaries; pairs naturally with Riverpod's `AsyncValue` in the UI; eliminates the "did I forget try/catch?" class of bugs.
- **Riverpod 2.x with `riverpod_generator` codegen** — chosen during `/setup-wizard` and `/constitute`. Rationale: less boilerplate than BLoC, autoDispose by default with codegen, built-in DI removes need for `get_it`, `AsyncValue<T>` composes cleanly with `Either<Failure, T>`.
- **`freezed` for entities, DTOs, and sealed unions** — chosen during `/constitute`. Rationale: hand-rolled equality is bug-prone; freezed gives `==`, `hashCode`, `copyWith`, sealed unions, and JSON for free.
- **`drift` for the local SQLite database** (over sqflite/isar) — chosen during `/constitute`. Rationale: typed queries, strong migration tooling, pairs cleanly with strict mode. Isar is in maintenance; sqflite is untyped strings.
- **`go_router` for routing** — chosen during `/constitute`. Rationale: official Flutter routing solution, supports deep links and type-safe routes.
- **`flutter_test + mocktail` for testing** — chosen during `/setup-wizard`. Rationale: no codegen step (unlike mockito), null-safe, official runner.
- **No backend / fully local** — chosen during `/constitute`. Rationale: medication data is sensitive PHI; eliminating cloud sync is the strongest privacy posture and simplest architecture.
- **Maximum strictness lint mode** (`strict-casts`, `strict-inference`, `strict-raw-types`, no `dynamic`, no `!`) — chosen during `/constitute`. Rationale: medication tracking is safety-relevant; type-system bugs can cause real harm.
- **All timestamps in UTC, displayed in local** — Rationale: prevents DST and time-zone bugs in adherence calculations.
- **`Clock` injection over `DateTime.now()`** — Rationale: scheduling and adherence logic is the heart of the app; tests must control time.

## Naming Conventions

- **Filenames**: `snake_case.dart` (Effective Dart)
- **Types / classes / widgets / enums**: `UpperCamelCase`
- **Variables / parameters / methods**: `lowerCamelCase`
- **Constants**: `lowerCamelCase` (Dart style, NOT `SCREAMING_SNAKE_CASE`)
- **Private members**: leading underscore `_thing`
- **Use cases**: imperative verb phrase, one operation per class — `AddMedication`, `MarkIntake`, `GetTodaySchedule`
- **Repositories (abstract)**: noun + `Repository` — `MedicationRepository`
- **Repository implementations**: `<Name>RepositoryImpl` in `data/repositories/`
- **Failures**: noun + `Failure` suffix
- **Entities**: domain noun, no suffix — `Medication`, `Schedule`, `Intake`
- **DTOs**: entity name + `Model` suffix — `MedicationModel`
- **Drift tables**: plural PascalCase — `Medications`, `Intakes`
- **Riverpod providers (codegen)**: `xxxProvider` auto-generated from `@riverpod` annotated function

## Domain Cheat Sheet

- **Entities**: `Medication`, `MedicationForm` (enum: tablet, capsule, injection, syrup, drops, inhaler, cream, sachet), `MedicationType` (sealed: `Course` | `Permanent`), `Dosage`, `Schedule`, `TimeSlot`, `Intake`, `IntakeStatus` (pending, taken, missed, skipped), `AdherenceRecord`, `Settings`
- **Intake state machine**: `pending → taken/skipped/missed`. `taken → pending` allowed within `gracePeriodMinutes` (undo).
- **Adherence formula**: weekly = `sum(taken across week) / sum(scheduled across week)`. Skipped intakes do NOT count toward scheduled. Future intakes don't dilute the ratio.
- **Default settings**: `gracePeriodMinutes = 5`, `intakeWindowMinutes = 120`, `notificationLeadMinutes = 0`
- **Privacy rule**: notification text must NOT contain medication names — generic "Time for your medication" + tap to view details

## Known Pitfalls
<!-- Populated during work as mistakes are discovered -->

- **`package:flutter/*` in `domain/`** — strictly forbidden. Domain must run in pure Dart tests.
- **`package:drift/*` or `package:flutter_local_notifications/*` in `domain/`** — also forbidden. Wrap in repositories / services.
- **`!` null assertion** — every use is a latent runtime crash. Use explicit null checks or pattern matching.
- **`SharedPreferences` for medication/intake data** — never. That's the system of record; it goes in drift.
- **`ref.read` inside provider `build`** — breaks reactivity. Use `ref.watch`.
- **`DateTime.now()` in domain code** — never. Inject `Clock` and use `Clock.now()` so tests can fake time.
- **Direct `flutter_local_notifications` calls from features** — never. Always go through `core/notifications/notification_service.dart`.
- **Logging medication names** — forbidden. PHI even for personal use.
- **Drift schema changes without bumped `schemaVersion` and migration** — never drop or alter columns blindly; this is health data, do not lose it.
- **`BuildContext` after `await` without `mounted` check** — `use_build_context_synchronously` lint catches this; keep it on.
- **Assuming Flutter's default locale fallback lands on English** _(Feature 006, Task 007)_: `flutter gen-l10n` emits `supportedLocales` alphabetically by locale code — for `[de, en, uk]` the list starts with `de`, not `en`. Flutter's default `BasicLocaleListResolutionCallback` falls back to the FIRST entry when no match, so unsupported device locales silently resolve to German. **Fix**: always wire an explicit `localeResolutionCallback` that matches by `languageCode` and returns `const Locale('en')` (or the intended fallback) explicitly. Never rely on list ordering. Discovered only because a `Locale('fr')` test asserted English strings and failed — confirms the value of testing unsupported-locale fallback, not just supported locales.
- **Context7 / docs lag Flutter SDK reality** _(Feature 006, Task 002)_: Research said `synthetic-package: false` is the modern recommendation. Flutter 3.41+ has **fully retired** the option entirely — any value emits a deprecation warning. Lesson: when adopting Flutter config flags mentioned in docs, also run `flutter pub get` and read the stderr. Omitting the flag = current desired behavior. Treat Flutter migration docs as "at least this old" and verify against the running toolchain.
- **Riverpod codegen strips `Notifier` suffix from class names** _(Feature 015 / Task 003)_: `riverpod_generator 4.x` derives the provider symbol from a class-form notifier by stripping a trailing `Notifier` and appending `Provider`. So `class FooNotifier extends _$FooNotifier` emits `fooProvider`, NOT `fooNotifierProvider`. To keep the canonical class-form symbol shape, pass `name: 'fooNotifierProvider'` on the annotation. The code-reviewer in this task initially flagged the `name:` parameter as redundant — repair-agent verified removing it produces 18+ `undefined_identifier` errors at every consumer call site. The `name:` parameter is load-bearing, not stylistic.

- **Class-form `@riverpod` notifiers default to autoDispose; manual `NotifierProvider<>` defaulted to keepAlive** _(Feature 015 / Task 003)_: The lifetime semantic flips when migrating from manual `final fooProvider = NotifierProvider<>(...)` to `@riverpod class Foo`. Default `@riverpod` is autoDispose. For notifiers that own a resource initialized in `build()` (e.g., a `StreamController` registered via `ref.onDispose`), autoDispose will close and re-create the resource between sequential `container.read()` calls in unit tests, breaking "multiple sequential emissions" assertions. Use `@Riverpod(keepAlive: true)` to preserve the original implicit lifetime. Pair with the `name:` parameter (above) for class-form notifiers.

- **Constitution §7.4 `analysis_options.yaml` was never actually applied** _(Feature 012 / Task 001)_: The constitution's §7.4 prescribes a strict-mode analyzer config (strict-casts, strict-inference, strict-raw-types, freezed-required `invalid_annotation_target: ignore`, exclude globs for `**/*.g.dart` + `**/*.freezed.dart`, 20 lint rules), but the actual `analysis_options.yaml` was the bare Flutter scaffold default with NONE of this. Discovered when Task 001 of spec 012 went to introduce the first `@freezed` class — without the exclude glob, the generated `*.freezed.dart` would have been linted with strict mode. Brought into compliance during a Task 001 addendum. **Lesson**: when the constitution prescribes file content, `/setup-wizard` or `/constitute` should actually apply it — don't assume the prescription is in effect just because the constitution says so. Verify the file matches before downstream tasks rely on it. Two lint rules deferred (`directives_ordering`, `sort_pub_dependencies`) with documented in-file rationale because their fix would have required out-of-scope edits to `test/` and a `pubspec.yaml` reshuffle — both deferred to a future lint-hardening pass.

- **AC wording inherited from memory can be load-bearing — verify against the compiler before stamping it as a contract** _(Feature 017 / Task 001)_: Spec 017's AC-1 inherited "`@freezed abstract sealed class Failure`" verbatim from MEMORY L163's `abstract`-keyword rule. The rule was correct for the case it was originally written for (non-sealed `@freezed abstract class AppSettings`) but the new spec applied it to a **sealed** union, where Dart 3 rejects the combination with "A 'sealed' class can't be marked 'abstract' because it's already implicitly abstract." The constitution §3.2 example itself omits `abstract` — the load-bearing source was right, the memory line was over-broad. Caught at Task 001 codegen time by the architect agent; spec.md AC-1 was amended in-place, and MEMORY L163 was rewritten to distinguish the two cases (non-sealed → `abstract` required; sealed → `abstract` forbidden). **Pattern**: when copying a contract claim from MEMORY into a spec's AC, verify by reading the constitution's primary source *and* by sketching the literal Dart line through the compiler if possible. Memory entries decay in scope as the codebase grows new shapes the original entry didn't anticipate.

- **Byte-identical-claim ACs (AC-8/9/10 in spec 017) are the strongest possible regression test of a "non-breaking migration" claim** _(Feature 017 / Tasks 001, /verify)_: When a spec's load-bearing claim is "this refactor changes the data shape but keeps every consumer compiling unchanged" (e.g., freezed factory redirects preserving `const CacheFailure('x')` literals + `isA<CacheFailure>()` matchers), encode that claim as ACs that `git diff main -- <path>` must produce zero output. Three such ACs in spec 017 (settings_repository_impl.dart, settings_provider.dart source, all of test/features/settings/) caught zero regressions because the implementation was correct — but they would have caught **any** drift instantly and made the verdict trivial. Trade-off: byte-identical ACs are brittle if the spec ever needs to amend the consumer files (then they must be downgraded to "literal-call-site-preserving edits only"). Use them when the migration is intentionally non-behavioral and the spec explicitly forbids consumer-file edits. Generated `.g.dart` regeneration is NOT a violation if AC scopes to the source `.dart` file — be explicit about generated vs source in the AC wording.

- **`/review` can legitimately expand scope to *other* bugs, not the spec being reviewed** _(Feature 017 / /review)_: Security review of spec 017's `Failure.unknown(Object error, ...)` surfaced a CWE-209/CWE-532 risk that becomes weaponizable only when a typed logger lands (bug 017). The right response was NOT to expand spec 017 (which is intentionally non-behavioral and doesn't introduce any production call site of `Failure.unknown`), but to **add a scoped finding to `bugs/017-typed-logger-missing.md`** — specifically a per-variant redact/allowlist disposition table that the bug's eventual `/specify` must include in the sanitize layer. Pattern: when a /review finding is forward-looking (no current consumer can trigger it) and a tracking bug already exists for the consumer system, append the finding to that bug as a scope addition rather than expanding the current spec. Keeps the current spec's surface narrow and the deferral chain documented and actionable.

## What Worked
<!-- Patterns and approaches that solved problems well -->

- **Hand-coded `const ColorScheme` literals + per-hex assertion tests** _(Feature 001)_: 70 per-field `expect(scheme.x, const Color(0x...))` tests catch any design drift instantly. Matched spec §9 drift-protection intent. Total cost: ~120 lines of test file, huge ROI.
- **SHA-256 hashing for bundled font assets** _(Task 001)_: `SOURCE.md` records hashes of all four Roboto TTFs. Security-reviewer independently verified them — excellent supply-chain hygiene for a personal app. Consider promoting to a CI check later.
- **`ValueNotifier<ThemeMode>` + `ListenableBuilder` for app-wide theme state** _(Task 004+008)_: zero dependencies, built into Flutter, trivially testable, pairs cleanly with `MaterialApp.themeMode`. Appropriate choice when you don't need Riverpod yet.
- **Task bundling for mechanical glue work** _(spec 001 breakdown)_: bundling "create data structure + write data-assertion tests" into one task (Task 002, Task 004) kept the breakdown to 8 tasks instead of 11 without losing rigor. Matched `_multi-task-continuation.md` bundling rule.
- **Deferring manual cross-platform run to user** _(Task 008 + AC-13)_: sandbox can't drive simulators. Widget smoke test exercises the compile pipeline so AC-13 is the ONLY gap at verify time, and it's clearly scoped as "user runs `flutter run -d ios/android` after merge."
- **`ListenableBuilder` + `MaterialApp.router` + top-level `GoRouter` constant coexist cleanly** _(Task 004, Feature 002)_: Wrapping `MaterialApp.router(routerConfig: appRouter)` in a `ListenableBuilder(listenable: themeController)` rebuilds `MaterialApp.router` on theme change without resetting `GoRouter`'s internal navigation stack. The `GoRouter` instance is a top-level `final` constant (same shape as `themeController`); `MaterialApp.router` re-reads `routerConfig` on each build but doesn't reconstruct the router. Confirmed by `flutter test` passing through navigation-then-cycling in one test flow. This is the reactive-theme-plus-go_router pattern dosly will use going forward.
- **Integration-gate task ordering for UI refactors** _(Task 004 → 005, Feature 002)_: When swapping `MaterialApp` for `MaterialApp.router`, the existing widget tests that assert on the old `home:` target will fail at task 004 completion. Correct response: task 004's `Done when` deliberately OMITS `flutter test` (gates only on `dart analyze`), and task 005's `Done when` includes `flutter test` + `flutter build apk --debug` as the integration verification point. Kept the breakdown honest and avoided a spurious "task 004 broke tests" panic.
- **`lucide_icons_flutter` package is the right Lucide fit for Flutter** _(Feature 004)_: Package name is `lucide_icons_flutter` (NOT `lucide_icons` — that's a different/older package). Import is `package:lucide_icons_flutter/lucide_icons.dart`, class is `LucideIcons`, API is `static const IconData` drop-in for `Icons.*`. Version ^3.1.12 tree-shakes unused glyphs in release builds. All standard Lucide names compile in lowerCamelCase (verified: `pill`, `house`, `settings`, `history`, `circlePlus`, `thermometer`, `syringe`, `glasses`, `droplets`, `activity`, `clock`, `check`, `chevronDown`, `chevronRight`, `arrowLeft`, `search`, `plus`, `eye`, `x`, `phone`, `sunMoon`, `sun`, `moon`). No name surprises — follow lucide.dev naming directly.
- **Two-task breakdowns for mechanical swaps are fine** _(Feature 004)_: A dependency-add + icon-swap migration across 2 screens doesn't need 4 tasks. Task 001 (infra: add dep) + Task 002 (presentation: swap + showcase) cleanly separated by layer. Splitting icon swap into per-screen tasks would have been over-granularization.
- **Top-level `_noop(int _) {}` preserves `const` on widgets with required callback params** _(Feature 005, Task 001)_: Flutter widgets like `NavigationBar` require `onDestinationSelected` to be supplied. An inline lambda `(_) {}` is NOT `const`-compatible, so `const HomeBottomNav()` would fail to compile if the widget embedded one. Workaround: declare a private top-level function `void _noop(int _) {}` in the same file and pass it by reference — top-level functions ARE const-compatible in Dart, so `const HomeBottomNav()` works at every call site. Use this pattern for any "presentational only, will-become-real-later" widget that wraps a Material control with a required callback.
- **Flutter built-in `NavigationBar` delivers M3 pill-indicator + ColorScheme theming for free** _(Feature 005)_: The spec asked for a widget that "looks exactly like" an HTML `.bot-nav` with surface-container bg, secondary-container pill, on-surface-variant → on-surface label color swap. `NavigationBar` does all of this automatically by reading `Theme.of(context).colorScheme` — zero `NavigationBarThemeData` customization, zero hard-coded colors, zero light/dark duplication. When the HTML design was generated from Material Theme Builder (as here), the built-in widget is the answer; custom Row-based replicas are churn.
- **Two-task breakdown with per-task integration-gate separation stayed honest** _(Feature 005)_: Task 001 (widget + wire, gated on `dart analyze` + existing-test no-regression) and Task 002 (widget test, gated on full `flutter test` + `flutter build apk --debug`) followed the Feature 002 pattern — pushing the build/test integration gate to the terminal task of the feature. Both tasks' done-when conditions were satisfiable independently, and the full gate ran exactly once. No repair loops needed.
- **Mid-feature UX refactor (sheet → full-screen modal) cost was ~1 agent run after `/verify`-time feedback** _(Feature 011, 2026-04-30)_: User rejected the bottom-sheet visual after Tasks 001-003 had shipped clean. Post-impl refactor swapped `showModalBottomSheet` for `Navigator.push(MaterialPageRoute(fullscreenDialog: true, ...))` via `rootNavigator: true`, renamed files via `git mv` (`*_sheet*` → `*_modal*`), rewrote the widget body from `Padding+Column+Text` to `Scaffold+AppBar+IconButton+Text`, adjusted the screen test's modal group, and rewrote the widget test's structure assertions. Net delta: 184/184 tests still pass, `dart analyze` clean, debug APK builds. **Lesson**: post-`/verify` user feedback that swaps the WIDGET TYPE (rather than internal structure) costs roughly the same as a single new task — file renames, widget rewrite, test rewrite, no domain/data churn. Acceptable cost for course-correction. Recorded the refactor in spec.md/plan.md as in-place AC text revisions with date markers ("AC-3 _(revised 2026-04-30)_") rather than rewriting history — gives the next reader an audit trail of what shipped vs. what was originally specced. Pattern reusable for any future post-impl spec revision.

- **Reviewing inert/stateless widgets rarely turns up findings** _(Feature 005)_: Security-reviewer + performance-analyst + qa-engineer all returned clean verdicts on a 3-file, no-I/O, no-state presentation change. Takeaway: keep /review in the pipeline even for tiny features (the "nothing found" report is itself a useful provenance record for audit mode), but don't expect it to justify expanding the widget. For future presentation-only micro-features, the review pass is cheap insurance but not a bottleneck.
- **Centralize sanctioned `!` null-assertions via a `BuildContext` extension** _(Feature 006, /review hardening)_: When the constitution forbids `!` but a framework pattern demands it (e.g., Flutter's `AppLocalizations.of(context)!`), hide it in a named getter: `extension AppLocalizationsContext on BuildContext { AppLocalizations get l10n => AppLocalizations.of(this)!; }`. Consumer widgets call `context.l10n.xxx` with zero `!` at the call site. Net effect: exactly one auditable `!` site in the entire codebase instead of N (one per widget). Scales perfectly — adding a new localized widget adds zero new `!` sites. Pattern should be reused for any future "framework returns nullable but it's never null in practice" primitive.
- **`/review` surface-area catches drift that per-task `code-reviewer` misses** _(Feature 006)_: Per-task code review looked at each changed file in isolation and never noticed that the feature had ended up with TWO `!` sites across the codebase (each file had its own compliant `1 !`, but the aggregate was 2). The feature-wide security-reviewer running during `/review` caught it immediately. Takeaway: keep `/review` in the pipeline even when per-task reviews all passed — feature-level security review surfaces aggregate-level issues (total `!` count, dependency pinning consistency, PHI exposure across surfaces) that single-file reviews cannot.
- **Running `/review` findings can still be fixed before `/verify`** _(Feature 006)_: Medium-severity review findings (unpinned dep + 2 `!` sites) were raised during `/review`, user asked to fix both, fixes applied (intl pinned + extension introduced), verified clean, then `/verify` ran. review.md stayed as the time-of-review snapshot; verify.md documented the follow-up resolution. This is the right pattern — don't re-run `/review` after every micro-fix, but do note the resolution trail in the verify report for audit clarity.
- **Repair agent as a safety net for incorrect code-review findings** _(Feature 015 / Task 003)_: Code-reviewer flagged the `name: 'settingsNotifierProvider'` annotation parameter as redundant. Repair agent attempted removal — produced 18+ `undefined_identifier` errors at every consumer call site, immediately confirming the parameter is load-bearing (codegen strips `Notifier` suffix). Lesson: when the implementing agent disagrees with a code-review finding, attempting the change in a controlled repair pass is the right move — compilation errors surface the truth fast. Don't blindly accept reviewer suggestions, but don't reject them without verifying either.

- **When `/review` finds a Medium severity finding, the Settings feature or post-MVP cleanup is NOT the default destination** _(Feature 006)_: Tempting to defer "Medium" to "later" but the cost of fixing while code is fresh is tiny; the cost of fixing later (with new context, forgotten reasoning, churned codebase) is large. For small Medium findings (< 20 lines to fix), the right default is fix-now. For larger ones, defer — but record a bug file so the deferral is visible.

- **Spinning off a sibling bug file mid-`/specify` keeps deferral chains visible** _(Feature 013, 2026-05-01)_: Bug 002's description name-checked a separate-but-related gap ("the typed logger doesn't exist yet, which is itself a separate gap") that wasn't filed anywhere. During `/specify` Phase 2 clarification I created `bugs/017-typed-logger-missing.md` BEFORE writing the spec, then spec §6 Out of Scope cross-referenced both bug 003 and bug 017 with named files. Net effect: the deferral chain is concrete (two real numbered bug files) instead of vague ("there's also this other thing somewhere"). Pattern reusable: any time a `/specify` clarification surfaces a related-but-out-of-scope gap, file the bug FIRST, then deliberately defer it in spec §6 with a file reference. Avoids the "TODO that gets lost" failure mode.

- **Surgical-fix specs (1-source-file, ≤5-AC delta) work cleanly with a 2-task breakdown: source + docs/bookkeeping** _(Feature 013, 2026-05-01)_: For tightly-scoped lint-violation fixes (4 `debugPrint` removals + import cleanup + 1 doc snippet + 1 bug front-matter flip), the right shape is one source-edit task (mobile-engineer) followed by one docs-and-bug-bookkeeping task (tech-writer). Kept the per-agent boundary clean (mobile-engineer doesn't touch `bugs/`, tech-writer doesn't touch `lib/`), let the integration gate run on the source task only (build/test/analyze), and made bookkeeping a low-risk doc-only second task. Two reviewers returned APPROVE with zero findings; aggregate `/review` returned clean across all three streams. Total wall-clock: ~5 minutes. Don't over-bundle (single task touching source + docs + bugs would mix agent expertise) and don't over-split (3+ tasks for ≤4 file edits is breakdown bloat).

- **`/verify` rightly distinguishes "implementation satisfies AC" from "test coverage breadth"** _(Feature 014, 2026-05-08)_: AC-9/AC-10 prescribed verification by widget test; the test exists for English locale and asserts the localized text + the `Text` widget content. The de/uk locale parity gap and the missing `behavior: SnackBarBehavior.floating` property assertion are coverage-breadth gaps, NOT contract violations — the implementation satisfies the AC text. Marked AC-9 and AC-10 PASS but flagged the gaps as Warning issues. Pattern: when an AC's wording specifies "verified by a widget test", check whether ANY widget test satisfies that wording; if so, AC is PASS. Coverage gaps go to the Issues list as Warnings, not as AC FAIL. Avoids the trap of conflating "test breadth" with "AC failure" — both matter, but distinctly.

- **Side-channel `StreamProvider<Failure>` is the right architecture for surfacing notifier-mutator failures to the UI when state shape is sync** _(Feature 014, 2026-05-07)_: Bug 003 sketched `AsyncNotifier<AppSettings>` as the "preferred" fix for silent error swallowing. Rejected during `/specify` because (a) initial load is sync and never fails, so wrapping the whole state in `AsyncValue` adds a phantom loading/error state that consumers must handle for no real benefit; (b) every existing consumer (`app.dart`, two selectors, theme preview) would need `.when(data, error, loading)`-unwrapping. Chose Option B from the bug's sketch: notifier owns a `late final StreamController<Failure> _errors` initialized **as the first statement** of `build()` with `ref.onDispose(_errors.close)` registered second, exposes a `Stream<Failure> get errors` getter, and a top-level `final settingsErrorsProvider = StreamProvider<Failure>((ref) => ref.watch(settingsProvider.notifier).errors)` bridges it. UI consumes via `ref.listen<AsyncValue<Failure>>(...)` + `.whenData((_) { ... showSnackBar })` to skip loading/error sentinels and only fire on actual emission. Smallest blast radius (only the notifier file + the screen change); state shape unchanged; mutator return types unchanged; all existing consumers untouched. Documented as the canonical pattern in `docs/architecture.md` (Feature 014) — reuse for any future feature whose mutator-failure surfacing needs grow.

- **`pump()` between an async tap and `pump(Duration)` for a SnackBar enter animation is fragile** _(Feature 014, 2026-05-07)_: A widget test doing `await tester.tap(...); await tester.pump(); await tester.pump(const Duration(milliseconds: 100));` to verify a SnackBar shown via `ref.listen` works **only because the underlying fake's `async` body has no internal `await`** — one microtask drain happens to suffice. If the fake ever gains an `await` (e.g., to simulate latency), the chain becomes "tap → pump (schedule) → pump(100ms) (animation tick before mutator resolves) → expect()" and the SnackBar hasn't been shown yet at expect time, silently failing in a hard-to-diagnose way. Defensive pattern: use TWO bare `pump()` calls (first to schedule, second to drain async resolution) followed by `pump(Duration(milliseconds: 100))` for the SnackBar enter animation. `pumpAndSettle()` is wrong for this — its loop hangs forever on the SnackBar enter animation. Code-reviewer caught this as a Warning in Feature 014 Task 003; not fixed in-task because the current fake has no `await`s, but the pattern should be defensive in any future "test a SnackBar after a tap" widget test.

When in doubt: read the HTML mock structure — if the mock has its own AppBar with a back/close icon-button leading + title, the user wants a full-screen modal; if the mock is a half-height card sliding from the bottom, then it's a sheet. Feature 011 spec/plan committed to bottom-sheet first; user rejected ("look absolutely different from HTML"). Refactored to `MaterialPageRoute(fullscreenDialog: true)` with `rootNavigator: true` so the modal covers the AppShell's bottom nav. **Lesson**: `/specify` Phase 2 should clarify modal type explicitly when the user says "modal" + supplies a HTML reference — do not default to bottom sheet without confirmation, because in M3-on-Flutter the visual difference is huge and the refactor cost (rename files + rewrite widget shape + rewrite tests) is non-trivial.

- **`MaterialPageRoute(fullscreenDialog: true) + rootNavigator: true` is the canonical full-screen modal pattern in a `StatefulShellRoute` app** _(Feature 011 refactor, 2026-04-30)_: With `go_router`'s `StatefulShellRoute.indexedStack`, each branch screen has its own inner Navigator nested under the outer `AppShell` Scaffold. Pushing a route via `Navigator.of(context).push(...)` lands on the INNER navigator and the AppShell's `bottomNavigationBar` stays visible — wrong for a full-screen modal. Fix: `Navigator.of(context, rootNavigator: true).push(MaterialPageRoute<void>(fullscreenDialog: true, builder: (_) => const Modal()))`. The `rootNavigator: true` flag walks up to the top-level Navigator (above the StatefulShellRoute) so the new modal route covers the entire viewport including the bottom nav. The modal widget itself should be a self-contained `Scaffold` with its own `AppBar` (back-arrow `IconButton` leading + title) — this is what the user expects to see and what HTML "modal" mocks usually depict. Reuse this pattern any time a feature opens a full-screen overlay from a tab branch.

- **`MaterialLocalizations.of(context).backButtonTooltip` covers the back-arrow tooltip without a new ARB key** _(Feature 011 refactor, 2026-04-30)_: Flutter ships locale-aware "Back" tooltips out of the box (`MaterialLocalizations.of(context).backButtonTooltip` returns "Back"/"Zurück"/"Назад" etc. for every supported locale). When adding a back-arrow `IconButton` as `AppBar.leading`, do NOT add a new ARB key for the tooltip — use this getter. Saves a translation, eliminates a translator-managed string, and stays in sync with Flutter's locale data automatically. Pattern: any time a tooltip / accessibility label is a generic UI verb ("Back", "Close", "Cancel", "OK"), check `MaterialLocalizations` first before adding a feature-specific ARB key.

- **`showModalBottomSheet` route-level chrome flows through M3 defaults — pass nothing but `useSafeArea: true`** _(Feature 011, Task 003)_: When the bottom-sheet body is a pure content widget (e.g. placeholder `AddMedicationSheet` rendering only a title), do NOT pass `backgroundColor`, `shape`, `elevation`, or `barrierColor` to `showModalBottomSheet`. With `useMaterial3: true`, the modal route uses `colorScheme.surfaceContainerLow` for the background, applies the M3 rounded-top shape, and provides scrim + drag-down dismissal automatically. Canonical call shape: `showModalBottomSheet<void>(context: context, useSafeArea: true, builder: (_) => const Body())`. Crucially, `useSafeArea: true` handles iOS home-indicator inset AT THE ROUTE LEVEL — the body widget itself must NOT also wrap in `SafeArea`, or you double-pad. For placeholder/preview sheets, the body should be a Padding+Column+Text and nothing else.

- **`FloatingActionButton` cannot be `const` — apply `const` to its `child` Icon instead** _(Feature 011, Task 003)_: Mirrors the `NavigationBar`-no-`const`-constructor lesson from Feature 005. `FloatingActionButton` does NOT declare a `const` constructor (it accepts `onPressed: VoidCallback?` which is generally non-const at call sites). So `MedsScreen.build` cannot return a fully `const` tree once a FAB is added. Fix: push `const` to the deepest leaves — `FloatingActionButton(onPressed: ..., tooltip: ..., child: const Icon(LucideIcons.plus))`. The `Icon` IS const-able and `prefer_const_constructors` is satisfied at the leaf even though the FAB itself is non-const. Generalizes: any Material widget that rejects `const` on its outer node should still receive `const` at every const-eligible child.

- **`tester.widget<Icon>(find.descendant(of: ..., matching: ...))` is the `!`-free way to inspect a widget's child in tests** _(Feature 011, Task 003)_: Direct access via `(fab.child! as Icon).icon` requires `!` to coerce nullable. The `descendant` finder + `tester.widget<T>` reads the correct widget instance from the tree without nullable coercion. Pattern: when a test needs to assert a property of a child widget, never reach for `parent.child!` — use `find.descendant(of: find.byType(Parent), matching: find.byType(Child))` and `tester.widget<Child>(...)`. Reuse this any time you need to verify "the FAB contains a Lucide icon", "the AppBar's leading is a back button", "the ListTile has a trailing chevron", etc.

- **Spec-prescribed UI control may be superseded by an in-flight UX refactor** _(Feature 010, post-Task 004 refactor)_: Spec §3.5 prescribed `RadioListTile<AppLanguage>` × 3 rows. After Task 004 shipped (using `RadioGroup` + RadioListTile per the Flutter 3.32+ deprecation), the user requested a refactor to a single dropdown to scale better with future Settings sections. /refactor handled this cleanly. **Lesson**: when `/verify` runs, accept user-approved post-task refactor deviations from spec text as valid IF the spec's behavioural contract (the AC) is still satisfied. Capture the deviation in verify.md's AC-X row with explicit "Implementation Deviation" justification. Do NOT mark the AC as PARTIAL/FAIL just because the prescriptive widget choice changed — the contract is the AC text, not the spec body's prescription.

- **Integration gate is where spec assumptions die** _(Feature 012 / Task 004)_: spec 012's research.md, §3.6, and AC-8 all confidently asserted that `SharedPreferencesWithCache.getString` returns `null` on a key whose stored value is an int (legacy data from a prior build). The qa-engineer running the integration gate found this assumption to be false — the platform layer throws `TypeError`. AC-8 was implemented with a workaround (`{'themeMode': '1'}` string seed), the agent escalated, and a small architect call added a `try/catch` in `getThemeMode()` that genuinely satisfies AC-8 with the real `int 1` seed. **Lesson**: research-derived platform-behavior assumptions baked into specs are the riskiest specs — verify them at the earliest test that can prove them, ideally before /breakdown. The user's `/fix bugs/001 — with 1 condition: when u have drafted fix, do impact analysis. If fix produces another bug — revise your fix. Do this loop until no issues` instinct is exactly the right reflex; it caught a real launch-day crash that would have hit any pre-spec-012 device upgrading. In future specs, when research.md asserts platform behavior, add an explicit AC that exercises the asserted behavior with a real platform test (not just a unit test against a fake) so the gate runs early.

- **Multi-task `/execute-task all` is a viable workflow when each task has a focused scope and explicit out-of-scope guards** _(Feature 012, full chain Tasks 001-005)_: User said "execute all 5 tasks"; the chain ran sequentially with per-task agent + verification + code-review. Three real defects surfaced and were fixed inline (analyzer config drift, freezed `abstract` keyword, legacy-int crash) without breaking the chain. Pattern: each task file's `Change details` enumerated explicit out-of-scope-bug boundaries (bug 002, 003, 004, 005, 010, 011 etc.) so the architect/qa-engineer agents wouldn't drive-by-fix unrelated audit findings. The boundaries held; reviewer verified no out-of-scope drift occurred. **Lesson**: when bundling related fixes into one spec but explicitly deferring others, write the deferrals into the task file's procedure block — not just the spec's §6 "Out of Scope" section. Agents read task files more carefully than spec sections.

## Performance Notes

- **Profile in profile mode**, never debug. Debug mode disables many optimizations and gives misleading numbers.
- **`const` constructors are free wins** — every widget that takes only compile-time constants should be `const`. The `prefer_const_constructors` lint enforces this.
- **`ListView.builder` over `ListView(children: [...])`** for any list that might exceed ~10 items.
- **Today's schedule resolution** runs on every app foreground; keep it pure and synchronous so the UI stays responsive.
