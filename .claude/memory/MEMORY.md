# Project Memory — dosly

## Project Identity
**dosly** is a personal cross-platform (iOS + Android) medication tracking app. Fully local — no backend, no accounts, no telemetry. Tracks medications, schedules, intake confirmations, and adherence history. Constitution at `constitution.md` is the source of truth.

## Project Structure
Greenfield Flutter app — `flutter create .` has run, scaffolding is in place. `linux/`, `macos/`, `web/`, `windows/` were removed (iOS + Android only). No feature code yet — first scaffolding step is `lib/core/error/failures.dart` per constitution Section 7.1.

## Architecture Decisions
<!-- Why decisions were made, not just what -->

- **Clean Architecture (data/domain/presentation per feature)** — chosen during `/setup-wizard`. Rationale: enforces dependency direction, makes domain logic unit-testable in pure Dart, isolates third-party SDK choices in `data/`.
- **`Either<Failure, T>` via fpdart** — chosen during `/setup-wizard`. Rationale: explicit error flow at repository boundaries; pairs naturally with Riverpod's `AsyncValue` in the UI; eliminates the "did I forget try/catch?" class of bugs.
- **Riverpod 2.x with `riverpod_generator` codegen** — chosen during `/setup-wizard` and `/constitute`. Rationale: less boilerplate than BLoC, autoDispose by default with codegen, built-in DI removes need for `get_it`, `AsyncValue<T>` composes cleanly with `Either<Failure, T>`.
- **`freezed` for entities, DTOs, and sealed unions** — chosen during `/constitute`. Rationale: hand-rolled equality is bug-prone; freezed gives `==`, `hashCode`, `copyWith`, sealed unions, and JSON for free.
- **`drift` for the local SQLite database** (over sqflite/isar) — chosen during `/constitute`. Rationale: typed queries, strong migration tooling, pairs cleanly with strict mode. Isar is in maintenance; sqflite is untyped strings.
- **`go_router` for routing** — chosen during `/constitute`. Rationale: official Flutter routing solution, supports deep links and type-safe routes.
- **`flutter_test + mocktail` for testing** — chosen during `/setup-wizard`. Rationale: no codegen step (unlike mockito), null-safe, official runner.
- **No backend / fully local** — chosen during `/constitute`. Rationale: medication data is sensitive PHI; eliminating cloud sync is the strongest privacy posture and simplest architecture.
- **Maximum strictness lint mode** (`strict-casts`, `strict-inference`, `strict-raw-types`, no `dynamic`, no `!`) — chosen during `/constitute`. Rationale: medication tracking is safety-relevant; type-system bugs can cause real harm.
- **All timestamps in UTC, displayed in local** — Rationale: prevents DST and time-zone bugs in adherence calculations.
- **`Clock` injection over `DateTime.now()`** — Rationale: scheduling and adherence logic is the heart of the app; tests must control time.
- **`lib/core/routing/` is the sanctioned composition-root exception to "core must be feature-agnostic" (§2.1)** _(Feature 023, Bug 015)_: Feature-aware shell widgets (the bottom nav with hardcoded Today/Meds/History destinations) belong beside `app_shell.dart`/`app_router.dart` in `core/routing/`, NOT in `core/widgets/`. `app_router.dart` already imports all four feature screens to build the `StatefulShellRoute`, so routing inherently knows the feature IA — that's the accepted layering exception. `core/widgets/` must hold only genuinely feature-agnostic widgets (e.g. `splash_screen.dart`, `prefs_load_error_screen.dart`). Rejected alternatives: a new `lib/app/` layer (not in the §2.2 directory layout) and parameterizing the nav's `destinations` (speculative generality — no second nav composition exists). When relocating between same-depth dirs under `lib/core/X/`, relative imports like `../../l10n/...` stay UNCHANGED.

- **§2.1 composition-seam exception: `@riverpod` provider files MAY import `data/`** _(Audit 2026-06-08 fix, 2026-06-09)_: The constitution's §2.1/§4.2 "presentation never imports `data/`" contradicted its own §7.2 Pattern Reference (which shows a `presentation/providers` file importing `data/repositories/...Impl`). Resolved by AMENDING §2.1 (not the code): a `@riverpod` provider file may import `data/` SOLELY to construct the repository/data-source it exposes as a `domain/`-typed provider (the DI composition seam). Screens/widgets/view-models still NEVER import `data/`. Mirrors the `core/routing/` carve-out. **Consequence for future audits/reviews/`/security`**: do NOT flag `settings_provider.dart` (or any provider file) importing `data/datasources` + `data/repositories` to wire a repo — it is sanctioned. Flag only non-provider files (screens/widgets) that reach into `data/`.

## Naming Conventions

- **Filenames**: `snake_case.dart` (Effective Dart)
- **Types / classes / widgets / enums**: `UpperCamelCase`
- **Variables / parameters / methods**: `lowerCamelCase`
- **Constants**: `lowerCamelCase` (Dart style, NOT `SCREAMING_SNAKE_CASE`)
- **Private members**: leading underscore `_thing`
- **Use cases**: imperative verb phrase, one operation per class — `AddMedication`, `MarkIntake`, `GetTodaySchedule`
- **Repositories (abstract)**: noun + `Repository` — `MedicationRepository`
- **Repository implementations**: `<Name>RepositoryImpl` in `data/repositories/`
- **Failures**: noun + `Failure` suffix
- **Entities**: domain noun, no suffix — `Medication`, `Schedule`, `Intake`
- **DTOs**: entity name + `Model` suffix — `MedicationModel`
- **Drift tables**: plural PascalCase — `Medications`, `Intakes`
- **Riverpod providers (codegen)**: `xxxProvider` auto-generated from `@riverpod` annotated function

## Domain Cheat Sheet

- **Entities**: `Medication`, `MedicationForm` (enum: tablet, capsule, injection, syrup, drops, inhaler, cream, sachet), `MedicationType` (sealed: `Course` | `Permanent`), `Dosage`, `Schedule`, `TimeSlot`, `Intake`, `IntakeStatus` (pending, taken, missed, skipped), `AdherenceRecord`, `Settings`
- **Intake state machine**: `pending → taken/skipped/missed`. `taken → pending` allowed within `gracePeriodMinutes` (undo).
- **Adherence formula**: weekly = `sum(taken across week) / sum(scheduled across week)`. Skipped intakes do NOT count toward scheduled. Future intakes don't dilute the ratio.
- **Default settings**: `gracePeriodMinutes = 5`, `intakeWindowMinutes = 120`, `notificationLeadMinutes = 0`
- **Privacy rule**: notification text must NOT contain medication names — generic "Time for your medication" + tap to view details

## Known Pitfalls
<!-- Populated during work as mistakes are discovered -->

- **`package:flutter/*` in `domain/`** — strictly forbidden. Domain must run in pure Dart tests.
- **`package:drift/*` or `package:flutter_local_notifications/*` in `domain/`** — also forbidden. Wrap in repositories / services.
- **`!` null assertion** — every use is a latent runtime crash. Use explicit null checks or pattern matching.
- **`SharedPreferences` for medication/intake data** — never. That's the system of record; it goes in drift.
- **`ref.read` inside provider `build`** — breaks reactivity. Use `ref.watch`.
- **`DateTime.now()` in domain code** — never. Inject `Clock` and use `Clock.now()` so tests can fake time.
- **Direct `flutter_local_notifications` calls from features** — never. Always go through `core/notifications/notification_service.dart`.
- **Logging medication names** — forbidden. PHI even for personal use.
- **Drift schema changes without bumped `schemaVersion` and migration** — never drop or alter columns blindly; this is health data, do not lose it.
- **`BuildContext` after `await` without `mounted` check** — `use_build_context_synchronously` lint catches this; keep it on.
- **Assuming Flutter's default locale fallback lands on English** _(Feature 006, Task 007)_: `flutter gen-l10n` emits `supportedLocales` alphabetically by locale code — for `[de, en, uk]` the list starts with `de`, not `en`. Flutter's default `BasicLocaleListResolutionCallback` falls back to the FIRST entry when no match, so unsupported device locales silently resolve to German. **Fix**: always wire an explicit `localeResolutionCallback` that matches by `languageCode` and returns `const Locale('en')` (or the intended fallback) explicitly. Never rely on list ordering. Discovered only because a `Locale('fr')` test asserted English strings and failed — confirms the value of testing unsupported-locale fallback, not just supported locales.
- **Context7 / docs lag Flutter SDK reality** _(Feature 006, Task 002)_: Research said `synthetic-package: false` is the modern recommendation. Flutter 3.41+ has **fully retired** the option entirely — any value emits a deprecation warning. Lesson: when adopting Flutter config flags mentioned in docs, also run `flutter pub get` and read the stderr. Omitting the flag = current desired behavior. Treat Flutter migration docs as "at least this old" and verify against the running toolchain.
- **Riverpod codegen strips `Notifier` suffix from class names** _(Feature 015 / Task 003)_: `riverpod_generator 4.x` derives the provider symbol from a class-form notifier by stripping a trailing `Notifier` and appending `Provider`. So `class FooNotifier extends _$FooNotifier` emits `fooProvider`, NOT `fooNotifierProvider`. To keep the canonical class-form symbol shape, pass `name: 'fooNotifierProvider'` on the annotation. The code-reviewer in this task initially flagged the `name:` parameter as redundant — repair-agent verified removing it produces 18+ `undefined_identifier` errors at every consumer call site. The `name:` parameter is load-bearing, not stylistic.

- **Class-form `@riverpod` notifiers default to autoDispose; manual `NotifierProvider<>` defaulted to keepAlive** _(Feature 015 / Task 003)_: The lifetime semantic flips when migrating from manual `final fooProvider = NotifierProvider<>(...)` to `@riverpod class Foo`. Default `@riverpod` is autoDispose. For notifiers that own a resource initialized in `build()` (e.g., a `StreamController` registered via `ref.onDispose`), autoDispose will close and re-create the resource between sequential `container.read()` calls in unit tests, breaking "multiple sequential emissions" assertions. Use `@Riverpod(keepAlive: true)` to preserve the original implicit lifetime. Pair with the `name:` parameter (above) for class-form notifiers.

- **Constitution §7.4 `analysis_options.yaml` was never actually applied** _(Feature 012 / Task 001)_: The constitution's §7.4 prescribes a strict-mode analyzer config (strict-casts, strict-inference, strict-raw-types, freezed-required `invalid_annotation_target: ignore`, exclude globs for `**/*.g.dart` + `**/*.freezed.dart`, 20 lint rules), but the actual `analysis_options.yaml` was the bare Flutter scaffold default with NONE of this. Discovered when Task 001 of spec 012 went to introduce the first `@freezed` class — without the exclude glob, the generated `*.freezed.dart` would have been linted with strict mode. Brought into compliance during a Task 001 addendum. **Lesson**: when the constitution prescribes file content, `/setup-wizard` or `/constitute` should actually apply it — don't assume the prescription is in effect just because the constitution says so. Verify the file matches before downstream tasks rely on it. Two lint rules deferred (`directives_ordering`, `sort_pub_dependencies`) with documented in-file rationale because their fix would have required out-of-scope edits to `test/` and a `pubspec.yaml` reshuffle — both deferred to a future lint-hardening pass.

- **AC wording inherited from memory can be load-bearing — verify against the compiler before stamping it as a contract** _(Feature 017 / Task 001)_: Spec 017's AC-1 inherited "`@freezed abstract sealed class Failure`" verbatim from MEMORY L163's `abstract`-keyword rule. The rule was correct for the case it was originally written for (non-sealed `@freezed abstract class AppSettings`) but the new spec applied it to a **sealed** union, where Dart 3 rejects the combination with "A 'sealed' class can't be marked 'abstract' because it's already implicitly abstract." The constitution §3.2 example itself omits `abstract` — the load-bearing source was right, the memory line was over-broad. Caught at Task 001 codegen time by the architect agent; spec.md AC-1 was amended in-place, and MEMORY L163 was rewritten to distinguish the two cases (non-sealed → `abstract` required; sealed → `abstract` forbidden). **Pattern**: when copying a contract claim from MEMORY into a spec's AC, verify by reading the constitution's primary source *and* by sketching the literal Dart line through the compiler if possible. Memory entries decay in scope as the codebase grows new shapes the original entry didn't anticipate.

- **Byte-identical-claim ACs (AC-8/9/10 in spec 017) are the strongest possible regression test of a "non-breaking migration" claim** _(Feature 017 / Tasks 001, /verify)_: When a spec's load-bearing claim is "this refactor changes the data shape but keeps every consumer compiling unchanged" (e.g., freezed factory redirects preserving `const CacheFailure('x')` literals + `isA<CacheFailure>()` matchers), encode that claim as ACs that `git diff main -- <path>` must produce zero output. Three such ACs in spec 017 (settings_repository_impl.dart, settings_provider.dart source, all of test/features/settings/) caught zero regressions because the implementation was correct — but they would have caught **any** drift instantly and made the verdict trivial. Trade-off: byte-identical ACs are brittle if the spec ever needs to amend the consumer files (then they must be downgraded to "literal-call-site-preserving edits only"). Use them when the migration is intentionally non-behavioral and the spec explicitly forbids consumer-file edits. Generated `.g.dart` regeneration is NOT a violation if AC scopes to the source `.dart` file — be explicit about generated vs source in the AC wording.

- **`/review` can legitimately expand scope to *other* bugs, not the spec being reviewed** _(Feature 017 / /review)_: Security review of spec 017's `Failure.unknown(Object error, ...)` surfaced a CWE-209/CWE-532 risk that becomes weaponizable only when a typed logger lands (bug 017). The right response was NOT to expand spec 017 (which is intentionally non-behavioral and doesn't introduce any production call site of `Failure.unknown`), but to **add a scoped finding to `bugs/017-typed-logger-missing.md`** — specifically a per-variant redact/allowlist disposition table that the bug's eventual `/specify` must include in the sanitize layer. Pattern: when a /review finding is forward-looking (no current consumer can trigger it) and a tracking bug already exists for the consumer system, append the finding to that bug as a scope addition rather than expanding the current spec. Keeps the current spec's surface narrow and the deferral chain documented and actionable.

- **`dart analyze` does NOT flag unused members of private classes (incl. in test files)** _(Feature 020 / Task 002)_: When deleting a test, any helper-class members that only that test consumed become dead code, but `dart analyze` stays green — `unused_element` does not fire for getters/methods on a private class like a `_FakeSettingsRepository`. In spec 020 the deleted theme-cycle widget test was the sole consumer of four recording getters (`lastSavedMode`, etc.); analyze reported "No issues found!" while the dead getters sat there. Only the code-reviewer caught it (constitution §3). **Lesson**: after deleting a test, manually grep the test file's shared fakes/helpers for now-orphaned members — do not trust `dart analyze` to surface them. Keep the code-review step for any deletion task; the toolchain has a real blind spot here.

- **A broadcast `StreamController.add()` inside a Notifier's `build()` is dropped — no subscriber is attached yet** _(Feature 022 / Task 003)_: `SettingsNotifier.build()` folds a failed `load()` to `_errors.add(failure)` to "surface" the error via `settingsErrorsProvider`. But `_errors` is a `broadcast` controller and `build()` runs before any widget subscribes, so the event is silently discarded (broadcast streams do not buffer for absent listeners). The line runs but reaches no one at startup. This is the behavior spec 022 **OQ-2 explicitly accepted** ("failures emitted while no listener is subscribed are simply not buffered ... acceptable"). Consequence for testing: the emission itself is **architecturally untestable** with a post-`build()` listener — the qa task could only assert the default-state fallback (the safety-critical, observable behavior) plus a companion test proving the stream still works for a *subsequent* save failure. **Lesson**: if startup load-failure surfacing ever needs to actually reach the UI (a real startup-error-UX spec), the fix is to defer the emit (`scheduleMicrotask(() => _errors.add(failure))`) OR replay-buffer the last failure (e.g. seed from a `StateProvider`/`ValueNotifier`) so a late subscriber sees it — and only then is the emission assertable. Don't write a test that subscribes after building and expects the build-time emission; it will either falsely pass (no assertion) or require the production change.

- **Type-compatible *variant* drift in a hand-written test double is invisible to `dart analyze` AND to assertions — only a fidelity review catches it** _(Bug 018, 2026-06-07)_: Feature 022 widened `SettingsRepositoryImpl.save*` failures from `CacheFailure` to `Failure.unknown(e, st)` but only realigned the in-scope notifier test; the screen test's `_FakeSettingsRepository` kept emitting `const Left(CacheFailure('mock failure'))` for a full feature cycle. Unlike an interface *signature* change — which breaks `dart analyze` project-wide and forces every fake to update atomically (see the "public-interface return-type change must land atomically" entry, Feature 022/Task 001) — a *variant* change keeps the fake compiling (both are valid `Failure`s) AND keeps the test green whenever the consumer discards the payload (`settings_screen.dart` does `next.whenData((_) => staticLocalizedString)`). So the divergence is caught by neither the compiler nor the test — only by review (it was a security-reviewer Info + code-reviewer note during /review). **Lesson**: when a scoped task changes *which* sealed-union variant a method returns (not its type signature), grep ALL sibling test doubles (`implements <Repo>` across `test/`) for the OLD variant — type-compatibility hides the rot, and the task's Affected Areas list won't mention out-of-scope fakes. The fix is mechanical (mirror the already-realigned sibling test, drop `const` since `Exception(...)` has no const ctor); the hard part is noticing it at all. Filed bug 020 for a pre-existing 1-of-4 save-error-path coverage gap surfaced during the same test assessment.

- **`DropdownButton` menu items render OFF-STAGE in widget tests even after `pumpAndSettle` — the idiomatic `find.text(item)` throws "Bad state: No element"** _(Bug 020, 2026-06-08)_: To drive a `DropdownButton<T>.onChanged` in a `flutter_test`, the standard recipe `tap(dropdown) → pumpAndSettle() → tap(find.text('Label').last)` FAILS here: after the menu route opens, its items stay off-stage, and `find.text` (default `skipOffstage: true`) matches zero widgets. Working pattern: `tap(find.byType(DropdownButton<T>))` → `pump()` (single frame, NOT pumpAndSettle) → locate via `find.descendant(of: find.byType(DropdownMenuItem<T>, skipOffstage: false), matching: find.text('Label', skipOffstage: false))` → `tap(item.last, warnIfMissed: false)` (the off-stage overlay means tap coordinates hit-test the underlying widget, but the gesture still dispatches to the item's onTap). Make the assertion self-validating so `warnIfMissed: false` can't hide a no-op tap: set up so the observable effect (e.g. an error SnackBar) can ONLY occur if `onChanged` actually fired. **Meta-lesson**: a code-reviewer flagged this off-stage idiom as "ugly, prefer pumpAndSettle"; a controlled experiment (apply the suggestion, run the test) proved the suggestion throws "No element" — the original was load-bearing. When a reviewer and the implementing agent disagree on whether a cleaner approach works, run it; the test result settles it in one shot (same pattern as the `name:`-parameter dispute, Feature 015/Task 003). Document the empirical constraint inline so the warning isn't re-raised.

- **`late final` field assigned inside a Riverpod `Notifier.build()` throws `LateInitializationError` on rebuild** _(Audit 2026-06-08 fix, 2026-06-09)_: Riverpod reuses the same Notifier instance across rebuilds and re-runs `build()` on it. A `late final StreamController _errors;` reassigned in `build()` works on first build but throws `LateInitializationError` if a watched dependency invalidates and `build()` re-runs. Use `late` (non-`final`). The canonical "StreamController created in `build()` + `ref.onDispose(controller.close)`" pattern is correct precisely because `ref.onDispose` fires on RECOMPUTE (not only on final disposal) — it closes the old controller before the new build creates a fresh one, so there is no leak and no `!` is needed in the getter. Was dormant in `SettingsNotifier` only because its deps never invalidate in production. A reviewer's suggested fix (`_errors.close()` at the top of `build()`) is WRONG: it crashes the first build (`late` uninitialised) or needs a forbidden `!`.
- **Zombie clusters survive `dart analyze` when public-by-codegen API + tests keep them "reachable"** _(Audit 2026-06-08 fix, 2026-06-09)_: The `CycleThemeMode` use case + its `@riverpod` provider + `SettingsNotifier.cycleThemeMode()` had ZERO UI callers (the theme UI uses `setUseSystemTheme`+`setThemeMode`), yet `dart analyze` stayed green because the provider is public-by-codegen and tests invoked the method. To find dead clusters: grep `lib/` (excluding the definition file + `*.g.dart`) for the method-INVOCATION pattern (e.g. `.cycleThemeMode(`); if the only callers are under `test/`, it is dead production code (§3.5). Companion to the existing "`dart analyze` does not flag unused members of private classes" note.
- **Do NOT "fix" the unguarded settings getters — the asymmetry is intentional and TEST-LOCKED** _(Audit 2026-06-10 /fix)_: The 2026-06-10 adversarial audit (architect) flagged `getManualLanguage()`'s unguarded `getString` read as an "asymmetry defect" vs the guarded `getThemeMode()`, recommending a `try/catch → en`. Applying it BROKE a deliberate spec-022 AC-2 test (`returns Left when manualLanguage is stored as an int`): wrong-type data is SUPPOSED to propagate to `SettingsRepositoryImpl.load()`'s `catch` → `Left(Failure.unknown)`. Only `getThemeMode()` is internally guarded (it had a documented legacy `int→String` migration); the other three getters are unguarded BY DESIGN with the repo-level catch as the single containment boundary (see the getThemeMode / L130 notes). The guard change is invisible to `dart analyze` AND the formatter — **only `flutter test` caught it**. Lesson: before adding defensive handling to a getter on an audit/`/fix` recommendation, grep `test/` for a contract test asserting the CURRENT propagation behavior; treat "make the siblings symmetric" findings on these getters as false positives. Resolution was revert-to-unguarded + a dartdoc documenting the intentional asymmetry. (Audit guards in the agent prompts must list "unguarded prefs getters are by-design" for the architect too, not just qa/security — its omission is what let this finding through.) Separately, running the new tall-style `dart format lib test` on a codebase last formatted by an older formatter reflowed **37 files** (CR1's "12" was `lib`-only; `test/` added ~25) and wrapped a long single-line `if` so it tripped `curly_braces_in_flow_control_structures` — add braces when the formatter splits an `if`/statement across lines.

## What Worked
<!-- Patterns and approaches that solved problems well -->

- **A test group named for the majority rule makes a deliberate minority exception look like a coverage hole — close it with a co-located, explicitly-named exception test, even when the behavior is already covered elsewhere** _(Bug 019, 2026-06-07)_: Feature 022's AC-2 ("wrong-type cache value never throws out of `load()`") is satisfied two ways: three unguarded settings keys let the `TypeError` propagate to `load()`'s outer catch → `Left(UnknownFailure)`, but `themeMode` is internally guarded in `getThemeMode()` (its own `try/catch` → `AppThemeMode.light`) → `Right(default)`. The AC-2 test group `load() — wrong-type cache values return Left` asserted `Left` for the three unguarded keys and omitted `themeMode` — even though `themeMode`'s wrong-type behavior WAS already green via a legacy-int(1) test in the generic `load()` group. The gap was purely discoverability: a reader of the AC-2 group would assume all four keys return `Left`. Fix = add ONE test IN the AC-2 group, named as "the guarded exception to the wrong-type→Left rule," using a wrong-type value DISTINCT from the existing probe (`double 2.5` vs the legacy `int 1`) so it reads as an independent assertion, not a copy. Now a future removal of `getThemeMode()`'s guard fails an AC-2-labelled test immediately. Lesson: when an AC is honored by different mechanisms across similar inputs, encode the exception as a named test co-located with the majority-rule group — test ORGANIZATION/discoverability is a regression contract, not just raw line coverage. Pairs with the honest-test-naming rule (Feature 024). No production change needed (the `getThemeMode()` dartdoc already documented the fallback).
- **Re-verify every sub-item of a stale consolidated audit bug against current code BEFORE specifying** _(Feature 024, 2026-05-28)_: Bug 016 bundled 10 audit-flagged coverage gaps from 2026-04-30. By spec time, 4 were dead: sub-items 4 & 7 had been closed by tests that landed in intervening specs, and 5 & 6 were moot because `theme_preview` was deleted in spec 020. The `/research` pass grepped each sub-item against HEAD and cut scope from 10 to 6 real items, and also corrected the bug's "4-way" duplication claim to the actual **7-way** (`grep -rn "_resolveLocale" test/`). Pattern: an audit/consolidated bug is a snapshot — its file:line evidence rots. Before `/specify`, verify each item still reproduces; mark closed/moot ones explicitly and record the corrected facts in the spec's Current State so `/plan` and `/breakdown` inherit reality, not the stale report. Saved ~40% of the nominal work and avoided writing tests for deleted code.
- **Honest test naming when a defensive branch is unreachable via the test harness** _(Feature 024 / Task 001)_: see [[bug-016]] and the External-API-Quirks line on `InMemorySharedPreferencesAsync` not throwing. When you cannot reach a production branch from the test double, assert the same observable OUTCOME via a reachable trigger and name the test for what it actually exercises (e.g. "...via fromCodeOrDefault orElse ... catch branch unreachable via InMemorySharedPreferencesAsync") rather than letting the name imply coverage it doesn't have. code-reviewer caught a first-draft name that claimed the `catch` branch; the fix was rename + comment, not faking a throw. Keeps coverage claims truthful for future `/verify` and `/audit` passes.

- **Single-choke-point logging via `Logger.root.onRecord` + a PURE sanitizer is the PHI-safe pattern** _(Feature 025, 2026-06-02)_: §4.2.1 needs a typed logger whose sanitize layer can't be bypassed. `package:logging` beat a bare `dart:developer` wrapper precisely because `Logger.root.onRecord` is ONE structural listener every record flows through — put `sanitizeRecord` there and bypass is impossible by construction (a wrapper relies on a lint nobody violates). Keep the sanitizer a PURE `sanitizeRecord(LogRecord, {required bool includeErrorDetail}) → SanitizedLog` in its own file (no `dart:developer`/Flutter/Riverpod imports) so it's unit-tested in isolation; the `Failure` dispatch is an exhaustive sealed `switch` with NO `default:` (a new variant breaks compilation → forces a redaction decision). Redact-by-default: emit only `runtimeType` for opaque/`UnknownFailure` errors, keep only provably-safe fields (`PermissionDeniedFailure.permission`, `ValidationFailure.field`); full `toString()` only when `includeErrorDetail == kDebugMode`. Bottom sheets are a specifically-Material pattern (half-height, drag-to-dismiss). When in doubt: read the HTML mock structure — if the mock has its own AppBar with a back/close icon-button leading + title, the user wants a full-screen modal; if the mock is a half-height card sliding from the bottom, then it's a sheet. Feature 011 spec/plan committed to bottom-sheet first; user rejected ("look absolutely different from HTML"). Refactored to `MaterialPageRoute(fullscreenDialog: true)` with `rootNavigator: true` so the modal covers the AppShell's bottom nav. **Lesson**: `/specify` Phase 2 should clarify modal type explicitly when the user says "modal" + supplies a HTML reference — do not default to bottom sheet without confirmation, because in M3-on-Flutter the visual difference is huge and the refactor cost (rename files + rewrite widget shape + rewrite tests) is non-trivial.

- **`MaterialPageRoute(fullscreenDialog: true) + rootNavigator: true` is the canonical full-screen modal pattern in a `StatefulShellRoute` app** _(Feature 011 refactor, 2026-04-30)_: With `go_router`'s `StatefulShellRoute.indexedStack`, each branch screen has its own inner Navigator nested under the outer `AppShell` Scaffold. Pushing a route via `Navigator.of(context).push(...)` lands on the INNER navigator and the AppShell's `bottomNavigationBar` stays visible — wrong for a full-screen modal. Fix: `Navigator.of(context, rootNavigator: true).push(MaterialPageRoute<void>(fullscreenDialog: true, builder: (_) => const Modal()))`. The `rootNavigator: true` flag walks up to the top-level Navigator (above the StatefulShellRoute) so the new modal route covers the entire viewport including the bottom nav. The modal widget itself should be a self-contained `Scaffold` with its own `AppBar` (back-arrow `IconButton` leading + title) — this is what the user expects to see and what HTML "modal" mocks usually depict. Reuse this pattern any time a feature opens a full-screen overlay from a tab branch.

- **`MaterialLocalizations.of(context).backButtonTooltip` covers the back-arrow tooltip without a new ARB key** _(Feature 011 refactor, 2026-04-30)_: Flutter ships locale-aware "Back" tooltips out of the box (`MaterialLocalizations.of(context).backButtonTooltip` returns "Back"/"Zurück"/"Назад" etc. for every supported locale). When adding a back-arrow `IconButton` as `AppBar.leading`, do NOT add a new ARB key for the tooltip — use this getter. Saves a translation, eliminates a translator-managed string, and stays in sync with Flutter's locale data automatically. Pattern: any time a tooltip / accessibility label is a generic UI verb ("Back", "Close", "Cancel", "OK"), check `MaterialLocalizations` first before adding a feature-specific ARB key.

- **`showModalBottomSheet` route-level chrome flows through M3 defaults — pass nothing but `useSafeArea: true`** _(Feature 011, Task 003)_: When the bottom-sheet body is a pure content widget (e.g. placeholder `AddMedicationSheet` rendering only a title), do NOT pass `backgroundColor`, `shape`, `elevation`, or `barrierColor` to `showModalBottomSheet`. With `useMaterial3: true`, the modal route uses `colorScheme.surfaceContainerLow` for the background, applies the M3 rounded-top shape, and provides scrim + drag-down dismissal automatically. Canonical call shape: `showModalBottomSheet<void>(context: context, useSafeArea: true, builder: (_) => const Body())`. Crucially, `useSafeArea: true` handles iOS home-indicator inset AT THE ROUTE LEVEL — the body widget itself must NOT also wrap in `SafeArea`, or you double-pad. For placeholder/preview sheets, the body should be a Padding+Column+Text and nothing else.

- **`FloatingActionButton` cannot be `const` — apply `const` to its `child` Icon instead** _(Feature 011, Task 003)_: Mirrors the `NavigationBar`-no-`const`-constructor lesson from Feature 005. `FloatingActionButton` does NOT declare a `const` constructor (it accepts `onPressed: VoidCallback?` which is generally non-const at call sites). So `MedsScreen.build` cannot return a fully `const` tree once a FAB is added. Fix: push `const` to the deepest leaves — `FloatingActionButton(onPressed: ..., tooltip: ..., child: const Icon(LucideIcons.plus))`. The `Icon` IS const-able and `prefer_const_constructors` is satisfied at the leaf even though the FAB itself is non-const. Generalizes: any Material widget that rejects `const` on its outer node should still receive `const` at every const-eligible child.

- **`tester.widget<Icon>(find.descendant(of: ..., matching: ...))` is the `!`-free way to inspect a widget's child in tests** _(Feature 011, Task 003)_: Direct access via `(fab.child! as Icon).icon` requires `!` to coerce nullable. The `descendant` finder + `tester.widget<T>` reads the correct widget instance from the tree without nullable coercion. Pattern: when a test needs to assert a property of a child widget, never reach for `parent.child!` — use `find.descendant(of: find.byType(Parent), matching: find.byType(Child))` and `tester.widget<Child>(...)`. Reuse this any time you need to verify "the FAB contains a Lucide icon", "the AppBar's leading is a back button", "the ListTile has a trailing chevron", etc.

- **Spec-prescribed UI control may be superseded by an in-flight UX refactor** _(Feature 010, post-Task 004 refactor)_: Spec §3.5 prescribed `RadioListTile<AppLanguage>` × 3 rows. After Task 004 shipped (using `RadioGroup` + RadioListTile per the Flutter 3.32+ deprecation), the user requested a refactor to a single dropdown to scale better with future Settings sections. /refactor handled this cleanly. **Lesson**: when `/verify` runs, accept user-approved post-task refactor deviations from spec text as valid IF the spec's behavioural contract (the AC) is still satisfied. Capture the deviation in verify.md's AC-X row with explicit "Implementation Deviation" justification. Do NOT mark the AC as PARTIAL/FAIL just because the prescriptive widget choice changed — the contract is the AC text, not the spec body's prescription.

- **Integration gate is where spec assumptions die** _(Feature 012 / Task 004)_: spec 012's research.md, §3.6, and AC-8 all confidently asserted that `SharedPreferencesWithCache.getString` returns `null` on a key whose stored value is an int (legacy data from a prior build). The qa-engineer running the integration gate found this assumption to be false — the platform layer throws `TypeError`. AC-8 was implemented with a workaround (`{'themeMode': '1'}` string seed), the agent escalated, and a small architect call added a `try/catch` in `getThemeMode()` that genuinely satisfies AC-8 with the real `int 1` seed. **Lesson**: research-derived platform-behavior assumptions baked into specs are the riskiest specs — verify them at the earliest test that can prove them, ideally before /breakdown. The user's `/fix bugs/001 — with 1 condition: when u have drafted fix, do impact analysis. If fix produces another bug — revise your fix. Do this loop until no issues` instinct is exactly the right reflex; it caught a real launch-day crash that would have hit any pre-spec-012 device upgrading. In future specs, when research.md asserts platform behavior, add an explicit AC that exercises the asserted behavior with a real platform test (not just a unit test against a fake) so the gate runs early.

- **`GoRouter.errorBuilder` is a top-level sibling of `routes:` and renders OUTSIDE `StatefulShellRoute` — no `AppBottomNav` visible** _(Feature 019, Task 002, 2026-05-18)_: When a `GoRouter` configuration has a `StatefulShellRoute.indexedStack` plus sibling top-level `GoRoute`s, the `errorBuilder:` parameter (passed as a sibling of `routes:`) fires for any unmatched path AND renders the error widget at the root navigator level — same layer as `/settings` and `/theme-preview` in dosly. The error widget is NOT wrapped in the `AppShell` Scaffold, so `find.byType(AppBottomNav) findsNothing` holds during the error state. Practical implication: the error widget should be a self-contained `Scaffold` (its own `AppBar`, its own `body`); do NOT assume the AppShell's bottomNavigationBar is available for "go back via tab" recovery. Pair this with `automaticallyImplyLeading: false` on the error-screen AppBar because the error path has no guaranteed previous frame to pop to (an inbound deep link is the canonical case) — give the user one explicit `FilledButton(onPressed: () => context.go('/'))` recovery action instead. Verified by Test 7 in `app_router_test.dart` (production `appRouter` provider, no overrides, push `/nonexistent`, assert `findsNothing` for `AppBottomNav` while on error screen, assert `findsOneWidget` for `AppBottomNav` after tapping "Go to home"). Reuse: any future feature that adds a `GoRouter` error handler in a shell-routed app should follow the same pattern — self-contained Scaffold + explicit-button recovery, not a back-arrow.

- **Three-task split (l10n → source+test → docs+bug) is the optimal grain for a small Flutter bug-fix spec with localized UX** _(Feature 019, 2026-05-18)_: Spec 019 (15 ACs, ~50 lines of diff) ran cleanly as three sequential tasks with zero repair attempts: Task 001 (mobile-engineer) ARB additions + `flutter gen-l10n`; Task 002 (mobile-engineer) source + integration test; Task 003 (tech-writer) bug closure + architecture-doc bullet. The l10n split is load-bearing because gen-l10n is a natural rollback boundary — if any ARB is missing a key, codegen fails before any source consumer is touched. The source+test bundling (rather than separate source / separate test tasks) worked because mobile-engineer can verify behavior end-to-end in one execution; the integration test IS the verification step. The tech-writer task is intentionally LAST so the bug-closure Resolution section can describe what actually shipped, not what was planned. This pattern generalizes for any small spec touching: (l10n keys + 1-2 source files + 1 test file + 1 bug closure + 1 doc bullet). Feature 018 used 2-task because no l10n was involved; Feature 019's add-l10n shape justifies the third task.

- **AC-3 prescribes test assertions and AC-2 prescribes structural elements — they can drift apart, so test-thoroughness gaps for a structural AC are not necessarily AC failures** _(Feature 019 /verify, 2026-05-18)_: Spec 019's AC-2 listed the body Text as a required structural element of the errorBuilder widget; AC-3 prescribed Test 7's exact assertions (title text, button presence, tap recovery — but NOT body text). The qa-engineer flagged Test 7's missing body-text assertion as a coverage gap against AC-2. The right verdict at /verify: AC-3 is fully covered (Test 7 follows its prescription verbatim) and AC-2 is covered by source-code inspection (the body Text IS in the build method). The gap is real but is a Warning-level test-thoroughness improvement, not an AC failure. Lesson for future specs: when AC-N prescribes the exact contents of a test (function names, expects, assertion strings), make sure those assertions cover every structural AC element the test is supposed to verify — otherwise you create a "structural AC verified by source inspection only, not by widget test" gap that surfaces at /review. Counter-pattern: write AC-3 as "Test X asserts every element listed in AC-2" rather than spelling out specific assertions. **BSD `sed`-escaped-brackets pitfall** _(also 2026-05-18)_: `sed -i '' 's/^- \[ \] \*\*AC-\([0-9]\+\)\*\*/- [x] **AC-\1**/'` failed silently on macOS — BSD sed handles `\[`, `\]`, `\(`, `\)`, `\+` differently than GNU sed. The `Edit` tool with `replace_all: true` on a non-overlapping unique prefix (`- [ ] **AC-`) succeeded cleanly. Future verify scripts should prefer the Edit tool for spec-checkbox transitions over BSD sed.

- **`grep -cE "PATTERN" file` exits 1 on zero matches and breaks `&&` chains in `/execute-task` Phase 3.2 verification scripts — same as MEMORY L193 surfacing again** _(Feature 019 /execute-task, 2026-05-18)_: Compound check `... && git diff main -- FILE | grep -cE "PATTERN" && dart analyze && flutter test ...` aborts after the first zero-match grep, silently skipping `dart analyze` + `flutter test`. The truncated output looked like a normal verification pass at first glance. Fix: prepend `set +e;` to the shell command, OR use independent `echo "label:"; grep -cE ...; echo "label:"; ...` statements so each predicate runs unconditionally. Second time this exact bug has bitten the verification step. Generalize: any verification batch that checks for the PRESENCE of zero-match-expected predicates (no new imports, no `!`, no debugPrint) needs `set +e` from the start.

- **Multi-task `/execute-task all` is a viable workflow when each task has a focused scope and explicit out-of-scope guards** _(Feature 012, full chain Tasks 001-005)_: User said "execute all 5 tasks"; the chain ran sequentially with per-task agent + verification + code-review. Three real defects surfaced and were fixed inline (analyzer config drift, freezed `abstract` keyword, legacy-int crash) without breaking the chain. Pattern: each task file's `Change details` enumerated explicit out-of-scope-bug boundaries (bug 002, 003, 004, 005, 010, 011 etc.) so the architect/qa-engineer agents wouldn't drive-by-fix unrelated audit findings. The boundaries held; reviewer verified no out-of-scope drift occurred. **Lesson**: when bundling related fixes into one spec but explicitly deferring others, write the deferrals into the task file's procedure block — not just the spec's §6 "Out of Scope" section. Agents read task files more carefully than spec sections.

## Performance Notes

- **Profile in profile mode**, never debug. Debug mode disables many optimizations and gives misleading numbers.
- **`const` constructors are free wins** — every widget that takes only compile-time constants should be `const`. The `prefer_const_constructors` lint enforces this.
- **`ListView.builder` over `ListView(children: [...])`** for any list that might exceed ~10 items.
- **Today's schedule resolution** runs on every app foreground; keep it pure and synchronous so the UI stays responsive.
