# Project Memory — dosly

## Project Identity
**dosly** is a personal cross-platform (iOS + Android) medication tracking app. Fully local — no backend, no accounts, no telemetry. Tracks medications, schedules, intake confirmations, and adherence history. Constitution at `constitution.md` is the source of truth.

## Project Structure
Greenfield Flutter app — `flutter create .` has run, scaffolding is in place. `linux/`, `macos/`, `web/`, `windows/` were removed (iOS + Android only). No feature code yet — first scaffolding step is `lib/core/error/failures.dart` per constitution Section 7.1.

## Architecture Decisions
<!-- Why decisions were made, not just what -->

- **Clean Architecture (data/domain/presentation per feature)** — chosen during `/setup-wizard`. Rationale: enforces dependency direction, makes domain logic unit-testable in pure Dart, isolates third-party SDK choices in `data/`.
- **`Either<Failure, T>` via fpdart** — chosen during `/setup-wizard`. Rationale: explicit error flow at repository boundaries; pairs naturally with Riverpod's `AsyncValue` in the UI; eliminates the "did I forget try/catch?" class of bugs.
- **Riverpod 2.x with `riverpod_generator` codegen** — chosen during `/setup-wizard` and `/constitute`. Rationale: less boilerplate than BLoC, autoDispose by default with codegen, built-in DI removes need for `get_it`, `AsyncValue<T>` composes cleanly with `Either<Failure, T>`.
- **`freezed` for entities, DTOs, and sealed unions** — chosen during `/constitute`. Rationale: hand-rolled equality is bug-prone; freezed gives `==`, `hashCode`, `copyWith`, sealed unions, and JSON for free.
- **`drift` for the local SQLite database** (over sqflite/isar) — chosen during `/constitute`. Rationale: typed queries, strong migration tooling, pairs cleanly with strict mode. Isar is in maintenance; sqflite is untyped strings.
- **`go_router` for routing** — chosen during `/constitute`. Rationale: official Flutter routing solution, supports deep links and type-safe routes.
- **`flutter_test + mocktail` for testing** — chosen during `/setup-wizard`. Rationale: no codegen step (unlike mockito), null-safe, official runner.
- **No backend / fully local** — chosen during `/constitute`. Rationale: medication data is sensitive PHI; eliminating cloud sync is the strongest privacy posture and simplest architecture.
- **Maximum strictness lint mode** (`strict-casts`, `strict-inference`, `strict-raw-types`, no `dynamic`, no `!`) — chosen during `/constitute`. Rationale: medication tracking is safety-relevant; type-system bugs can cause real harm.
- **All timestamps in UTC, displayed in local** — Rationale: prevents DST and time-zone bugs in adherence calculations.
- **`Clock` injection over `DateTime.now()`** — Rationale: scheduling and adherence logic is the heart of the app; tests must control time.
- **`lib/core/routing/` is the sanctioned composition-root exception to "core must be feature-agnostic" (§2.1)** _(Feature 023, Bug 015)_: Feature-aware shell widgets (the bottom nav with hardcoded Today/Meds/History destinations) belong beside `app_shell.dart`/`app_router.dart` in `core/routing/`, NOT in `core/widgets/`. `app_router.dart` already imports all four feature screens to build the `StatefulShellRoute`, so routing inherently knows the feature IA — that's the accepted layering exception. `core/widgets/` must hold only genuinely feature-agnostic widgets (e.g. `splash_screen.dart`, `prefs_load_error_screen.dart`). Rejected alternatives: a new `lib/app/` layer (not in the §2.2 directory layout) and parameterizing the nav's `destinations` (speculative generality — no second nav composition exists). When relocating between same-depth dirs under `lib/core/X/`, relative imports like `../../l10n/...` stay UNCHANGED.

- **§2.1 composition-seam exception: `@riverpod` provider files MAY import `data/`** _(Audit 2026-06-08 fix, 2026-06-09)_: The constitution's §2.1/§4.2 "presentation never imports `data/`" contradicted its own §7.2 Pattern Reference (which shows a `presentation/providers` file importing `data/repositories/...Impl`). Resolved by AMENDING §2.1 (not the code): a `@riverpod` provider file may import `data/` SOLELY to construct the repository/data-source it exposes as a `domain/`-typed provider (the DI composition seam). Screens/widgets/view-models still NEVER import `data/`. Mirrors the `core/routing/` carve-out. **Consequence for future audits/reviews/`/security`**: do NOT flag `settings_provider.dart` (or any provider file) importing `data/datasources` + `data/repositories` to wire a repo — it is sanctioned. Flag only non-provider files (screens/widgets) that reach into `data/`.

## Naming Conventions

- **Filenames**: `snake_case.dart` (Effective Dart)
- **Types / classes / widgets / enums**: `UpperCamelCase`
- **Variables / parameters / methods**: `lowerCamelCase`
- **Constants**: `lowerCamelCase` (Dart style, NOT `SCREAMING_SNAKE_CASE`)
- **Private members**: leading underscore `_thing`
- **Use cases**: imperative verb phrase, one operation per class — `AddMedication`, `MarkIntake`, `GetTodaySchedule`
- **Repositories (abstract)**: noun + `Repository` — `MedicationRepository`
- **Repository implementations**: `<Name>RepositoryImpl` in `data/repositories/`
- **Failures**: noun + `Failure` suffix
- **Entities**: domain noun, no suffix — `Medication`, `Schedule`, `Intake`
- **DTOs**: entity name + `Model` suffix — `MedicationModel`
- **Drift tables**: plural PascalCase — `Medications`, `Intakes`
- **Riverpod providers (codegen)**: `xxxProvider` auto-generated from `@riverpod` annotated function

## Domain Cheat Sheet

- **Entities** _(§5.1 amended 2026-06-16 — reconciled with the shipped add-medication form; see `research/2026-06-16-medication-entity-storage.md`)_: `Medication` (id, name, form, type, schedule, optional `dosePerIntake`, optional `stock`, notes, createdAt UTC), `MedicationForm` (enum: tablet, capsule, injection, syrup, drops, inhaler, cream, sachet), `MedicationType` (sealed: `Continuous{startDate}` | `Course{startDate, durationDays, pauseDays}` — endDate **derived**, `pauseDays>0` = cyclic; was `Permanent`/`Course{startDate,endDate}`), `Dosage` (`amount`+`unit` — **unifies** pill quantity-per-intake & liquid dose), `PackStock` (remaining/total/warnAt — pack forms only, NEW), `Schedule` (MVP defaults to `daily`; form has no frequency control yet), `TimeSlot` (`minuteOfDay` int, NOT Flutter `TimeOfDay` — domain stays Flutter-free), `Intake`, `IntakeStatus` (pending, taken, missed, skipped), `AdherenceRecord`, `Settings`. Storage = **drift** (not yet in `pubspec.yaml`; system of record per §4.2.1).
- **Intake state machine**: `pending → taken/skipped/missed`. `taken → pending` allowed within `gracePeriodMinutes` (undo).
- **Adherence formula**: weekly = `sum(taken across week) / sum(scheduled across week)`. Skipped intakes do NOT count toward scheduled. Future intakes don't dilute the ratio.
- **Default settings**: `gracePeriodMinutes = 5`, `intakeWindowMinutes = 120`, `notificationLeadMinutes = 0`
- **Privacy rule**: notification text must NOT contain medication names — generic "Time for your medication" + tap to view details

## Known Pitfalls
<!-- Populated during work as mistakes are discovered -->

- **Adding a method to a repository INTERFACE breaks every hand-written test fake that `implements` it — and per-task `dart analyze` on only the changed files won't catch it** _(Feature 037 / Task 001→008, 2026-07-01)_: Task 001 added `delete(MedicationId)` to `MedicationRepository`. Five hand-written fakes (`_FakeMedicationRepository`/`_LoadingMedicationRepository`/`_ErrorMedicationRepository` in `meds_screen_test.dart`; `_FakeMedicationRepository`/`_RecordingMedicationRepository` in `add_medication_modal_test.dart`) `implements MedicationRepository` without the new method → 5 "Missing concrete implementation of `MedicationRepository.delete`" errors, i.e. the WHOLE suite stops compiling. It slipped through Tasks 001/002 verification because those only ran `dart analyze` on the changed production files (domain/data dirs), not project-wide, and the broken fakes live in presentation test dirs. **Rules**: (1) when a task changes an abstract interface, `grep -rn "implements <Interface>" test/ lib/` and enumerate ALL implementers (prod + test fakes) as affected files in the breakdown; (2) run project-wide `dart analyze` (not just changed-file analyze) after any interface change; (3) minimal fix for unrelated fakes = add a no-op override (`Future<Either<Failure, void>> delete(...) async => const Right(null)`). Handled as discovered Task 008.
- **Adding a second in-flight async action to a widget needs a SYMMETRIC disable guard — disabling only the new button leaves the old one tappable mid-flight** _(Feature 037 / Task 005, 2026-07-01)_: The delete affordance added `_isDeleting` and correctly disabled the trash button on `(_isDeleting || _isSaving)`, but the pre-existing Save button still guarded only `_isSaving ? null : _onSave`. Because the delete flow sets `_isDeleting = true` only AFTER the confirm dialog closes (the modal barrier is gone by then), the Save button was live during the awaiting delete → a race between two non-idempotent mutations on the same `original.id` (an edit could be silently discarded; `mounted` guards prevented a crash but not the lost write). Caught at Task-005 code review, fixed by making Save symmetric: `(_isSaving || _isDeleting) ? null : _onSave`. **Rule**: when you add an in-flight flag for a new async action to a screen that already has other async actions, update EVERY action's `onPressed` guard to disable on the union of all in-flight flags, not just its own.
- **Parameterizing an add-form for EDIT silently WIPES every field the form doesn't collect, because the edit use case does `original.copyWith(<only the collected fields>)`** _(Feature 036 / Task 007, 2026-06-19)_: Spec 036 reused `AddMedicationModal` for edit by adding `Medication? initial` + pre-fill. The `_onSave` builds the same args the add path builds (name/form/intakeMinutes/type/dosePerIntake/stock) and the `EditMedication` use case does `original.copyWith(name:.., type:.., schedule:.., dosePerIntake:.., stock:.., notes: notes)`. TWO fields the form has no control for were being silently overwritten: (1) **`notes`** — the modal never passes notes, so the param defaulted to `null` and `copyWith(notes: null)` WIPED any existing notes; fix = pass `notes: original.notes` in the edit-branch call. (2) **Continuous `startDate`** — `_onSave` always rebuilt `MedicationType.continuous(startDate: DateTime.utc(clock.now()...))`, so editing a continuous med RESET its start date to today; fix = `final originalType = widget.initial?.type; if (originalType is ContinuousType) startDate = originalType.startDate; else stamp today` (today is still correct for add and for a Course→Continuous switch). Both were caught at the Task-007 code-review checkpoint, NOT by tests (the add-form never sets notes, and intakes/startDate have no behavioral effect yet — so nothing was red). Also fixed at the use-case layer (Task 003 review): slot reconciliation keyed `minuteOfDay → TimeSlotId` dropped each unchanged slot's `doseOverride` — switched to keying `minuteOfDay → TimeSlot` and reusing the whole slot verbatim. **Rule**: when you turn an add-form into an add/edit form, enumerate EVERY field on the entity and confirm each is either (a) collected+editable in the form, or (b) explicitly forwarded from `original` so it round-traips unchanged. `copyWith` with a missing arg passes `null`/default and overwrites — it does NOT preserve. The spec's "fields the form doesn't collect round-trip unchanged" clause is the checklist; tests won't catch a wipe of a field that's always-null-from-the-form or not-yet-behavioral.
- **Editing an existing aggregate must NOT mint a new id or restamp `createdAt`; use `original.copyWith(...)` (don't pass id/createdAt) and a dedicated `update`/upsert path that does an in-place SQL UPDATE** _(Feature 036, 2026-06-19)_: `AddMedication` mints `MedicationId`+`createdAt`; the parallel `EditMedication` must preserve both by `copyWith`-ing the original and leaving id/createdAt out of the call. Persistence: a new `MedicationRepository.update` → `MedicationLocalDataSource.upsertMedication` uses drift **`insertOnConflictUpdate` (NOT `insertOrReplace`/`InsertMode.insertOrReplace`)** for the parent row — with the `TimeSlots.medicationId onDelete: cascade` FK, a REPLACE deletes+reinserts the parent and cascade-wipes ALL its child slots before reinsert; an upsert does an UPDATE and never fires the cascade. Child reconciliation = delete `where medicationId == id & id NOT IN incomingIds` then `insertOnConflictUpdate` each incoming child, all in one transaction (guard `slots.isNotEmpty` — `id NOT IN ()` matches every row in SQLite → another wipe footgun). Test caveat: slot-id PRESERVATION alone can't prove the cascade didn't fire (a REPLACE that reinserts the same payload ids looks identical) — an airtight proof needs a child row carrying state NOT in the payload (e.g. a future `Intakes` row referencing a kept `slotId`); logged a TODO for when Intakes lands.
- **`git rm` the wip.md, don't `rm` it** _(Feature 036, 2026-06-19; re-confirms the F031 line-85 lesson)_: Across a 10-task `/execute-task all` run, each Phase-4 "complete" step did `rm -f .claude/wip.md && git add lib/... specs/` — the `rm` deletes the working file but `git add lib/ specs/` does NOT stage the deletion, so `.claude/wip.md` stayed TRACKED at HEAD with stale "agent execution complete" content (then the next task re-created it). Caught at feature end via `git ls-files .claude/wip.md` (non-empty = still tracked). Use `git rm -f .claude/wip.md` (stages the deletion + removes the working file) in Phase 4.2, or `git add -A .claude/wip.md`. Otherwise the stale marker rides into the `/finalize` squash and can trip false crash-recovery on the next run.

- **Hot reload reports a false "`Null` is not a subtype of `bool`" after adding a field to a class with top-level `final`/`static` instances** _(Feature 028 / verify, 2026-06-14)_: Adding non-nullable fields (`hasDose`/`hasQuantity`/`hasStock`…) to `_MedFormOption` then **hot reloading** crashed on tap — `type 'Null' is not a subtype of type 'bool' of 'function result'` at `_MedFormOption.hasQuantity`, inside `_resetConditionalFields`. Root cause: the top-level `final List<_MedFormOption> _medFormOptions` is initialized ONCE; hot reload updates class/method code but does NOT re-run top-level/static initializers (or `initState`), so the list still held instances built by the OLD constructor with no storage for the new fields → reads as null. NOT a code defect (`dart analyze` clean; 305 tests pass from a clean build because tests rebuild instances each run). Fix = **hot RESTART** (capital `R` / IDE restart button), not hot reload. Rule: after adding fields to a class, or changing any top-level/static initializer, `initState`, or global state, hot RESTART — don't trust hot reload. When you see "Null is not a subtype of <non-nullable T>" on a field that provably has a default, suspect stale hot-reload state before touching the code.

- **Adding a dependency: use `flutter pub add <pkg>`, never hand-edit `pubspec.yaml`** _(Task 2 / Feature 030, 2026-06-15)_: Constitution §2.3 mandates `flutter pub add`. Task 002 promoted the transitive `clock` to direct by manually adding `clock: ^1.1.1` — functionally fine (resolved to 1.1.2, no downgrade), but flagged in review as a process violation. When promoting a transitive dep to direct or adding any package, run `flutter pub add <pkg>` so the constraint matches the resolved version and the convention holds.
- **`MaterialLocalizations.formatMediumDate` (en) = "Thu, Mar 26" — weekday + abbrev month + day, NO year** _(Task 3 / Feature 030, 2026-06-15)_: When asserting date text in widget tests, do NOT assume "Mar 26, 2026". The en medium format includes the weekday and omits the year. Compute expected strings from the actual API (or run once to see the output) rather than guessing. Same applies to other locales — use `formatMediumDate` output, not a hand-built string. Pairs with [[clock]] usage: wrap the whole test body in `withClock(Clock.fixed(...))` so the default date is deterministic.
- **Drift schema changes without bumped `schemaVersion` and migration** — never drop or alter columns blindly; this is health data, do not lose it.
- **`BuildContext` after `await` without `mounted` check** — `use_build_context_synchronously` lint catches this; keep it on.
- **Assuming Flutter's default locale fallback lands on English** _(Feature 006, Task 007)_: `flutter gen-l10n` emits `supportedLocales` alphabetically by locale code — for `[de, en, uk]` the list starts with `de`, not `en`. Flutter's default `BasicLocaleListResolutionCallback` falls back to the FIRST entry when no match, so unsupported device locales silently resolve to German. **Fix**: always wire an explicit `localeResolutionCallback` that matches by `languageCode` and returns `const Locale('en')` (or the intended fallback) explicitly. Never rely on list ordering. Discovered only because a `Locale('fr')` test asserted English strings and failed — confirms the value of testing unsupported-locale fallback, not just supported locales.
- **Context7 / docs lag Flutter SDK reality** _(Feature 006, Task 002)_: Research said `synthetic-package: false` is the modern recommendation. Flutter 3.41+ has **fully retired** the option entirely — any value emits a deprecation warning. Lesson: when adopting Flutter config flags mentioned in docs, also run `flutter pub get` and read the stderr. Omitting the flag = current desired behavior. Treat Flutter migration docs as "at least this old" and verify against the running toolchain.
- **Riverpod codegen strips `Notifier` suffix from class names** _(Feature 015 / Task 003)_: `riverpod_generator 4.x` derives the provider symbol from a class-form notifier by stripping a trailing `Notifier` and appending `Provider`. So `class FooNotifier extends _$FooNotifier` emits `fooProvider`, NOT `fooNotifierProvider`. To keep the canonical class-form symbol shape, pass `name: 'fooNotifierProvider'` on the annotation. The code-reviewer in this task initially flagged the `name:` parameter as redundant — repair-agent verified removing it produces 18+ `undefined_identifier` errors at every consumer call site. The `name:` parameter is load-bearing, not stylistic.

- **Class-form `@riverpod` notifiers default to autoDispose; manual `NotifierProvider<>` defaulted to keepAlive** _(Feature 015 / Task 003)_: The lifetime semantic flips when migrating from manual `final fooProvider = NotifierProvider<>(...)` to `@riverpod class Foo`. Default `@riverpod` is autoDispose. For notifiers that own a resource initialized in `build()` (e.g., a `StreamController` registered via `ref.onDispose`), autoDispose will close and re-create the resource between sequential `container.read()` calls in unit tests, breaking "multiple sequential emissions" assertions. Use `@Riverpod(keepAlive: true)` to preserve the original implicit lifetime. Pair with the `name:` parameter (above) for class-form notifiers.

- **Constitution §7.4 `analysis_options.yaml` was never actually applied** _(Feature 012 / Task 001)_: The constitution's §7.4 prescribes a strict-mode analyzer config (strict-casts, strict-inference, strict-raw-types, freezed-required `invalid_annotation_target: ignore`, exclude globs for `**/*.g.dart` + `**/*.freezed.dart`, 20 lint rules), but the actual `analysis_options.yaml` was the bare Flutter scaffold default with NONE of this. Discovered when Task 001 of spec 012 went to introduce the first `@freezed` class — without the exclude glob, the generated `*.freezed.dart` would have been linted with strict mode. Brought into compliance during a Task 001 addendum. **Lesson**: when the constitution prescribes file content, `/setup-wizard` or `/constitute` should actually apply it — don't assume the prescription is in effect just because the constitution says so. - **`DropdownButton<T>` disabled state is `onChanged: null`** _(Feature 010 refactor)_: Flutter's canonical disabled idiom for `DropdownButton` is to pass `null` to `onChanged`. The button greys, taps don't open the menu, but the `value:` still renders so the user sees the current selection. Mirrors `SegmentedButton.onSelectionChanged: null` and (pre-3.32) `RadioListTile.onChanged: null`. For "disabled but visible" controls in this codebase, prefer this over `enabled: false` (the M3 `enabled:` flag exists on some tiles but inconsistently across widget types). Set `isExpanded: true` and wrap in `SizedBox(width: double.infinity)` for full-width.
- **System-mode picker controls must show the device-resolved value, not the stored manual value** _(Feature 010 refactor follow-up)_: When a Settings picker has both a "use system X" toggle AND a manual selector (theme: SegmentedButton; language: DropdownButton), the manual selector — when toggle is ON — must display the value the SYSTEM is currently resolving, not the user's stale prior manual choice. ThemeSelector got this right via `displayedMode = useSystemTheme ? (systemBrightness == dark ? dark : light) : manualThemeMode`. LanguageSelector initially missed it: showed the stored `manualLanguage` even when system was on. Fixed by computing `displayedLanguage = useSystemLanguage ? deviceLanguageFromLocaleOf : manualLanguage`. Pattern to apply to ANY future "system-X + manual-X" picker pair: never bind the disabled control's `value:` directly to the stored manual value; always derive the displayed value from the SOURCE the system would use.
- **`/review` Info-level findings are still worth fixing pre-`/finalize` if the cost is one line** _(Feature 011, 2026-04-30)_: The first `/verify` ran on a feature with one Info-level review finding (stale ARB description) and rendered APPROVED. Auto mode could have rolled straight to `/summarize`. Instead, ran `/fix` on the Info item — single-line ARB edit, `flutter gen-l10n` regen, fresh `/review` confirmed RESOLVED, fresh `/verify` re-confirmed APPROVED. Total cost: ~2 minutes including agent latency. Total benefit: translator-facing description + IDE-hover dartdoc are now accurate. Rule of thumb: when an Info finding fits on one line and the file is fresh in mind, fix it pre-`/finalize`. The cost of fixing later (after the codebase moves on, the context is gone, and someone has to re-page in the rationale) is at least an order of magnitude higher than fixing now.

- **`flutter gen-l10n` copies ARB `@key.description` blocks into dartdoc on the abstract `AppLocalizations` getters** _(Feature 011 fix, 2026-04-30)_: When you change a `@`-description in the source ARB and run `flutter gen-l10n`, the regenerated `app_localizations.dart` updates the `///` dartdoc above the abstract `String get xxx;` declaration — so any wording drift in description blocks DOES propagate to IDE-hover documentation for code consumers. Treat ARB description blocks as living documentation, not just translator-only metadata. Whenever the implementation pivots in a way that contradicts a description block (e.g. sheet→modal swap), update the description and re-run `flutter gen-l10n` so the generated dartdoc and the source ARB stay aligned. Catch: this kind of drift is invisible to `dart analyze` and `flutter test` — only a security/code review reading the ARB's `@`-descriptions will catch it. Pattern: when you finish ANY post-implementation refactor that changes the WIDGET TYPE backing a localized surface, grep the ARB descriptions for words tied to the old type ("sheet", "dialog", "screen", "page") before declaring the refactor done.

- **"Modal" in user-facing requests usually means a full-screen modal route, NOT a bottom sheet** _(Feature 011, post-Task 003 refactor, 2026-04-30)_: When the user says "modal" with a HTML/web reference attached, default to interpreting it as a **full-screen modal route** (`Navigator.push(MaterialPageRoute(fullscreenDialog: true, ...))` pushed via `rootNavigator: true`), NOT `showModalBottomSheet`. Web "modal" typically means a full-screen overlay dialog that covers the entire viewport with its own AppBar/header — that's `MaterialPageRoute(fullscreenDialog: true)` in Flutter, not a bottom sheet. Bottom sheets are a specifically-Material pattern (half-height, drag-to-dismiss). When in doubt: read the HTML mock structure — if the mock has its own AppBar with a back/close icon-button leading + title, the user wants a full-screen modal; if the mock is a half-height card sliding from the bottom, then it's a sheet. Feature 011 spec/plan committed to bottom-sheet first; user rejected ("look absolutely different from HTML"). Refactored to `MaterialPageRoute(fullscreenDialog: true)` with `rootNavigator: true` so the modal covers the AppShell's bottom nav. **Lesson**: `/specify` Phase 2 should clarify modal type explicitly when the user says "modal" + supplies a HTML reference — do not default to bottom sheet without confirmation, because in M3-on-Flutter the visual difference is huge and the refactor cost (rename files + rewrite widget shape + rewrite tests) is non-trivial.

- **`MaterialPageRoute(fullscreenDialog: true) + rootNavigator: true` is the canonical full-screen modal pattern in a `StatefulShellRoute` app** _(Feature 011 refactor, 2026-04-30)_: With `go_router`'s `StatefulShellRoute.indexedStack`, each branch screen has its own inner Navigator nested under the outer `AppShell` Scaffold. Pushing a route via `Navigator.of(context).push(...)` lands on the INNER navigator and the AppShell's `bottomNavigationBar` stays visible — wrong for a full-screen modal. Fix: `Navigator.of(context, rootNavigator: true).push(MaterialPageRoute<void>(fullscreenDialog: true, builder: (_) => const Modal()))`. The `rootNavigator: true` flag walks up to the top-level Navigator (above the StatefulShellRoute) so the new modal route covers the entire viewport including the bottom nav. The modal widget itself should be a self-contained `Scaffold` with its own `AppBar` (back-arrow `IconButton` leading + title) — this is what the user expects to see and what HTML "modal" mocks usually depict. Reuse this pattern any time a feature opens a full-screen overlay from a tab branch.

- **`MaterialLocalizations.of(context).backButtonTooltip` covers the back-arrow tooltip without a new ARB key** _(Feature 011 refactor, 2026-04-30)_: Flutter ships locale-aware "Back" tooltips out of the box (`MaterialLocalizations.of(context).backButtonTooltip` returns "Back"/"Zurück"/"Назад" etc. for every supported locale). When adding a back-arrow `IconButton` as `AppBar.leading`, do NOT add a new ARB key for the tooltip — use this getter. Saves a translation, eliminates a translator-managed string, and stays in sync with Flutter's locale data automatically. Pattern: any time a tooltip / accessibility label is a generic UI verb ("Back", "Close", "Cancel", "OK"), check `MaterialLocalizations` first before adding a feature-specific ARB key.

- **`showModalBottomSheet` route-level chrome flows through M3 defaults — pass nothing but `useSafeArea: true`** _(Feature 011, Task 003)_: When the bottom-sheet body is a pure content widget (e.g. placeholder `AddMedicationSheet` rendering only a title), do NOT pass `backgroundColor`, `shape`, `elevation`, or `barrierColor` to `showModalBottomSheet`. With `useMaterial3: true`, the modal route uses `colorScheme.surfaceContainerLow` for the background, applies the M3 rounded-top shape, and provides scrim + drag-down dismissal automatically. Canonical call shape: `showModalBottomSheet<void>(context: context, useSafeArea: true, builder: (_) => const Body())`. Crucially, `useSafeArea: true` handles iOS home-indicator inset AT THE ROUTE LEVEL — the body widget itself must NOT also wrap in `SafeArea`, or you double-pad. For placeholder/preview sheets, the body should be a Padding+Column+Text and nothing else.

- **`FloatingActionButton` cannot be `const` — apply `const` to its `child` Icon instead** _(Feature 011, Task 003)_: Mirrors the `NavigationBar`-no-`const`-constructor lesson from Feature 005. `FloatingActionButton` does NOT declare a `const` constructor (it accepts `onPressed: VoidCallback?` which is generally non-const at call sites). So `MedsScreen.build` cannot return a fully `const` tree once a FAB is added. Fix: push `const` to the deepest leaves — `FloatingActionButton(onPressed: ..., tooltip: ..., child: const Icon(LucideIcons.plus))`. The `Icon` IS const-able and `prefer_const_constructors` is satisfied at the leaf even though the FAB itself is non-const. Generalizes: any Material widget that rejects `const` on its outer node should still receive `const` at every const-eligible child.

- **`tester.widget<Icon>(find.descendant(of: ..., matching: ...))` is the `!`-free way to inspect a widget's child in tests** _(Feature 011, Task 003)_: Direct access via `(fab.child! as Icon).icon` requires `!` to coerce nullable. The `descendant` finder + `tester.widget<T>` reads the correct widget instance from the tree without nullable coercion. Pattern: when a test needs to assert a property of a child widget, never reach for `parent.child!` — use `find.descendant(of: find.byType(Parent), matching: find.byType(Child))` and `tester.widget<Child>(...)`. Reuse this any time you need to verify "the FAB contains a Lucide icon", "the AppBar's leading is a back button", "the ListTile has a trailing chevron", etc.

- **Spec-prescribed UI control may be superseded by an in-flight UX refactor** _(Feature 010, post-Task 004 refactor)_: Spec §3.5 prescribed `RadioListTile<AppLanguage>` × 3 rows. After Task 004 shipped (using `RadioGroup` + RadioListTile per the Flutter 3.32+ deprecation), the user requested a refactor to a single dropdown to scale better with future Settings sections. /refactor handled this cleanly. **Lesson**: when `/verify` runs, accept user-approved post-task refactor deviations from spec text as valid IF the spec's behavioural contract (the AC) is still satisfied. Capture the deviation in verify.md's AC-X row with explicit "Implementation Deviation" justification. Do NOT mark the AC as PARTIAL/FAIL just because the prescriptive widget choice changed — the contract is the AC text, not the spec body's prescription.

- **Integration gate is where spec assumptions die** _(Feature 012 / Task 004)_: spec 012's research.md, §3.6, and AC-8 all confidently asserted that `SharedPreferencesWithCache.getString` returns `null` on a key whose stored value is an int (legacy data from a prior build). The qa-engineer running the integration gate found this assumption to be false — the platform layer throws `TypeError`. AC-8 was implemented with a workaround (`{'themeMode': '1'}` string seed), the agent escalated, and a small architect call added a `try/catch` in `getThemeMode()` that genuinely satisfies AC-8 with the real `int 1` seed. **Lesson**: research-derived platform-behavior assumptions baked into specs are the riskiest specs — verify them at the earliest test that can prove them, ideally before /breakdown. The user's `/fix bugs/001 — with 1 condition: when u have drafted fix, do impact analysis. If fix produces another bug — revise your fix. Do this loop until no issues` instinct is exactly the right reflex; it caught a real launch-day crash that would have hit any pre-spec-012 device upgrading. In future specs, when research.md asserts platform behavior, add an explicit AC that exercises the asserted behavior with a real platform test (not just a unit test against a fake) so the gate runs early.

- **`GoRouter.errorBuilder` is a top-level sibling of `routes:` and renders OUTSIDE `StatefulShellRoute` — no `AppBottomNav` visible** _(Feature 019, Task 002, 2026-05-18)_: When a `GoRouter` configuration has a `StatefulShellRoute.indexedStack` plus sibling top-level `GoRoute`s, the `errorBuilder:` parameter (passed as a sibling of `routes:`) fires for any unmatched path AND renders the error widget at the root navigator level — same layer as `/settings` and `/theme-preview` in dosly. The error widget is NOT wrapped in the `AppShell` Scaffold, so `find.byType(AppBottomNav) findsNothing` holds during the error state. Practical implication: the error widget should be a self-contained `Scaffold` (its own `AppBar`, its own `body`); do NOT assume the AppShell's bottomNavigationBar is available for "go back via tab" recovery. Pair this with `automaticallyImplyLeading: false` on the error-screen AppBar because the error path has no guaranteed previous frame to pop to (an inbound deep link is the canonical case) — give the user one explicit `FilledButton(onPressed: () => context.go('/'))` recovery action instead. Verified by Test 7 in `app_router_test.dart` (production `appRouter` provider, no overrides, push `/nonexistent`, assert `findsNothing` for `AppBottomNav` while on error screen, assert `findsOneWidget` for `AppBottomNav` after tapping "Go to home"). Reuse: any future feature that adds a `GoRouter` error handler in a shell-routed app should follow the same pattern — self-contained Scaffold + explicit-button recovery, not a back-arrow.

- **Three-task split (l10n → source+test → docs+bug) is the optimal grain for a small Flutter bug-fix spec with localized UX** _(Feature 019, 2026-05-18)_: Spec 019 (15 ACs, ~50 lines of diff) ran cleanly as three sequential tasks with zero repair attempts: Task 001 (mobile-engineer) ARB additions + `flutter gen-l10n`; Task 002 (mobile-engineer) source + integration test; Task 003 (tech-writer) bug closure + architecture-doc bullet. The l10n split is load-bearing because gen-l10n is a natural rollback boundary — if any ARB is missing a key, codegen fails before any source consumer is touched. The source+test bundling (rather than separate source / separate test tasks) worked because mobile-engineer can verify behavior end-to-end in one execution; the integration test IS the verification step. The tech-writer task is intentionally LAST so the bug-closure Resolution section can describe what actually shipped, not what was planned. This pattern generalizes for any small spec touching: (l10n keys + 1-2 source files + 1 test file + 1 bug closure + 1 doc bullet). Feature 018 used 2-task because no l10n was involved; Feature 019's add-l10n shape justifies the third task.

- **AC-3 prescribes test assertions and AC-2 prescribes structural elements — they can drift apart, so test-thoroughness gaps for a structural AC are not necessarily AC failures** _(Feature 019 /verify, 2026-05-18)_: Spec 019's AC-2 listed the body Text as a required structural element of the errorBuilder widget; AC-3 prescribed Test 7's exact assertions (title text, button presence, tap recovery — but NOT body text). The qa-engineer flagged Test 7's missing body-text assertion as a coverage gap against AC-2. The right verdict at /verify: AC-3 is fully covered (Test 7 follows its prescription verbatim) and AC-2 is covered by source-code inspection (the body Text IS in the build method). The gap is real but is a Warning-level test-thoroughness improvement, not an AC failure. Lesson for future specs: when AC-N prescribes the exact contents of a test (function names, expects, assertion strings), make sure those assertions cover every structural AC element the test is supposed to verify — otherwise you create a "structural AC verified by source inspection only, not by widget test" gap that surfaces at /review. Counter-pattern: write AC-3 as "Test X asserts every element listed in AC-2" rather than spelling out specific assertions. **BSD `sed`-escaped-brackets pitfall** _(also 2026-05-18)_: `sed -i '' 's/^- \[ \] \*\*AC-\([0-9]\+\)\*\*/- [x] **AC-\1**/'` failed silently on macOS — BSD sed handles `\[`, `\]`, `\(`, `\)`, `\+` differently than GNU sed. - **`grep -cE "PATTERN" file` exits 1 on zero matches and breaks `&&` chains in `/execute-task` Phase 3.2 verification scripts — same as MEMORY L193 surfacing again** _(Feature 019 /execute-task, 2026-05-18)_: Compound check `... && git diff main -- FILE | grep -cE "PATTERN" && dart analyze && flutter test ...` aborts after the first zero-match grep, silently skipping `dart analyze` + `flutter test`. The truncated output looked like a normal verification pass at first glance. Fix: prepend `set +e;` to the shell command, OR use independent `echo "label:"; grep -cE ...; echo "label:"; ...` statements so each predicate runs unconditionally. Second time this exact bug has bitten the verification step. Generalize: any verification batch that checks for the PRESENCE of zero-match-expected predicates (no new imports, no `!`, no debugPrint) needs `set +e` from the start.

- **Multi-task `/execute-task all` is a viable workflow when each task has a focused scope and explicit out-of-scope guards** _(Feature 012, full chain Tasks 001-005)_: User said "execute all 5 tasks"; the chain ran sequentially with per-task agent + verification + code-review. ## Performance Notes

- **Profile in profile mode**, never debug. Debug mode disables many optimizations and gives misleading numbers.
- **`const` constructors are free wins** — every widget that takes only compile-time constants should be `const`. The `prefer_const_constructors` lint enforces this.
- **`ListView.builder` over `ListView(children: [...])`** for any list that might exceed ~10 items.
- **Today's schedule resolution** runs on every app foreground; keep it pure and synchronous so the UI stays responsive.
